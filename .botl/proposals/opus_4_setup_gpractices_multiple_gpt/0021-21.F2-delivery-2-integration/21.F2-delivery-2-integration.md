## 15. HELP command

The HELP command must be extended to display the Phase 1 commands and the commands introduced in this delivery. At a minimum, it must show the following syntax:

USER CREATE;<FirstName>;<Surnames>;<DNI>;<Email>;<Password>;<Phone>;<Card> USER DELETE;<Email>;<Password> USER UPDATE;<Email>;<Password>;<Field>;<NewValue> SYSTEM DATE;<yyyy-MM-dd> SYSTEM PRICE;<Price> GROUP CREATE;<Identifier>;<Name> GROUP ADD;<Identifier>;<Email> GROUP REMOVE;<Identifier>;<Email> GROUP DELETE;<Identifier> TICKET CREATE;<identifier>;<email>;<date> TICKET DELETE;<identifier> GROUPTICKET CREATE;<identifier>;<group>;<date> GROUPTICKET DELETE;<identifier> ATTRACTION CREATE;<identifier>;<name>;<capacity> ATTRACTION ENTER;<attraction>;<ticket> ATTRACTION EXIT;<attraction>;<email> ATTRACTION LIST;<attraction> ATTRACTION STATUS;<attractionIdentifier> HELP EXIT

## 16. Technical restrictions

Delivery 2 must retain all the technical requirements established in previous phases.

The project must continue to use Java 21 and Maven and generate, using mvn package, an executable JAR that can be run interactively or with a command file. Databases, persistence frameworks, and external libraries are not permitted. Relationships between objects must be represented with objects and collections while those elements are loaded into memory; domain relationships must not be unnecessarily replaced by identifiers or strings. Relationships must respect the directions specified in this document:

- attractions know which users are inside them, but users do not know the attractions;
- individual tickets know the user for whom they were purchased, but users do not store their tickets;
- group tickets are composed of the individual tickets of users included in the purchase;
- group tickets hold a reference to the purchasing group while it exists; this reference may become null when the group is deleted;
- groups and users do not store references to purchased tickets.

The different ticket types must be part of a common abstraction through class extension and/or interface implementation. The design must reuse shared information and behavior, particularly price-related behavior. Group tickets must use composition to contain the individual tickets representing their members. A solution implementing each ticket type completely independently, without object-oriented inheritance or abstraction mechanisms, will not be considered valid. The system must use a single instance of the element responsible for central park management. Tickets for the current day or earlier dates may not be deleted through ticket deletion commands and must be preserved in the system’s historical record. The --fly execution mode must reuse the same repositories and persistence mechanisms as normal execution, changing only the paths used to store data. Phase 1 features may not be removed or replaced with features incompatible with the previous specification.

## 20. Submission conditions

The submission must consist of the URL of the same Git repository used during previous phases and the new executable JAR generated for this delivery.

The repository must be accessible to the laboratory instructors and retain the complete history from project creation in Phase 0 through the Phase 2 state. In addition to the source code, Maven project, and elements required in earlier deliveries, it must contain the PlantUML source file for the application design. Instructors must be able to build the project using:

```text
mvn package
```

and execute the resulting JAR with an external command file:

```text
java -jar target/nombre-aplicacion.jar input_fase2.txt
```

The same file must also be executable in temporary mode:

```text
java -jar target/nombre-aplicacion.jar --fly input_fase2.txt
```

After an execution with --fly ends, data generated during that execution must not remain on the system. The application must work without requiring an IDE, modifications to the source code, or additional configuration. The Git repository URL and executable JAR together constitute Delivery 2.
