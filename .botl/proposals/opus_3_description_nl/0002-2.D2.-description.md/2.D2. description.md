# Amusement Park — Delivery 2

## 1. Objective

The second delivery extends the system developed in Phase 1 by introducing the first features specific to the amusement park. From this delivery onward, users will be able to form groups, purchase tickets, and access the park’s different attractions. The objective of this phase is to work with relationships between objects, collections, inheritance, interfaces, association, and composition, while maintaining an appropriate distribution of responsibilities among system classes. All features developed in Phase 1 must remain available and work correctly. The application must continue to use Java 21, Maven, and Git, generate an executable JAR, and accept commands both from standard input and from a text file.

## 2. Phase 2 — Amusement Park Management

## 3. Central park management

The application must have a single object responsible for managing the overall state of the park during execution. This object will centralize access to the users, groups, tickets, and attractions existing in the system, and allow operations that relate these elements to be performed. No more than one instance of this object may exist during the same execution of the application. The chosen design must guarantee this regardless of where in the application access to central management is requested.

## 4. Configurable system state

### 4.1. Current system date

Park operations will depend on a current date. When the application starts, the system date will be the local date at the time execution begins. To facilitate testing, this date may be replaced during execution and must not depend solely on the actual date of the computer running the application. The following command will be added:

```text
SYSTEM DATE;<yyyy-MM-dd>
```

For example:

```text
SYSTEM DATE;2027-04-15
```

From that moment on, all date-dependent operations must regard April 15, 2027, as the current system date. The date may be modified as many times as necessary during a single execution.

### 4.2. Current ticket price

The system will maintain a current base ticket price. At the start of each execution, this price will be 40.00 euros. The price may be modified during execution using:

SYSTEM PRICE;<Price>

For example:

```text
SYSTEM PRICE;45.50
```

The specified price must represent a valid, positive monetary amount. The current system price will be used as the base price for new tickets created from that moment onward. Changing the price will not alter the price of tickets already created. For group tickets, the corresponding discount will be applied to the current system base price at the time of purchase. The value set with SYSTEM PRICE will affect only the current execution. When a new execution begins, the price will revert to 40.00 euros.

## 5. User groups

Registered users may be organized into groups. Each group will have a unique identifier, a name, and will consist of users who already exist in the system. A group is created using:

GROUP CREATE;Identifier;Name

For example:

```text
GROUP CREATE;G01;Familia Garcia
```

To add an existing user to a group, use:

GROUP ADD;Identifier;Email

For example:

```text
GROUP ADD;G01;ana@correo.com
GROUP ADD;G01;pedro@correo.com
```

The same user may not appear more than once in the same group. GROUP ADD must reject the addition of a user who already belongs to that group. A group may be created empty and users added progressively. It must also be possible to remove a user from a group while the group is modifiable:

GROUP REMOVE;Identifier;Email

A group may also be deleted using:

GROUP DELETE;Identifier

Deletion is permitted only if there is no group ticket associated with that group whose date is equal to or later than the current system date. Group tickets for earlier dates alone will not prevent deletion of the group. If the group has a future ticket, it may first be deleted using GROUPTICKET DELETE. A ticket for the current day cannot be deleted and will continue to prevent deletion of the group. A group has an active group ticket when at least one associated group ticket has a date equal to or later than the current system date. GROUP ADD and GROUP REMOVE may be performed only when the group has no associated active group tickets. Group tickets for earlier dates are considered historical and will not prevent group modification. If a future ticket is deleted using GROUPTICKET DELETE, the application must check again whether other active group tickets remain associated with the group. If none remain, the group can be modified again. The group’s locked state must not be stored as an independent attribute; instead, it must be determined from the existing tickets and the current system date.

## 6. Attractions

The park will contain different attractions. Each attraction must have at least:

- a unique identifier;
- a name;
- a maximum capacity;
- a collection of users currently inside it.

An attraction may be created using:

ATTRACTION CREATE;Identifier;Name;Capacity

For example:

```text
ATTRACTION CREATE;A01;Dragon Rojo;20
ATTRACTION CREATE;A02;Torre del Cielo;12
```

Capacity represents the maximum number of people who may be in an attraction simultaneously. The relationship between an attraction and its occupants will be unidirectional. The attraction must hold references to the users currently inside it, but users must not store any reference to the attraction they are in. The application must provide an easy way to consult the users currently in an attraction using:

ATTRACTION LIST;AttractionIdentifier

For example:

```text
ATTRACTION LIST;A01
```

The operation will display the email addresses of the users inside the attraction at that moment. If there are no users, it must produce an empty or equivalent result in a controlled way. This is a read-only operation and must not change the state of the attraction.

## 7. Tickets

To access attractions, users must have a ticket valid for the corresponding date. Individual tickets and group tickets are different types of ticket but share information and behavior. All tickets must have, at a minimum:

- a unique identifier;
- a date of use;
- information about their price.

All ticket types will share a common identifier space. An individual ticket and a group ticket may not simultaneously have the same identifier. This restriction must be checked in a common manner for the different ticket types. When creating a group ticket, it must also be checked that none of the identifiers derived for its constituent individual tickets conflicts with an existing ticket. If any identifier conflict occurs, the group ticket must not be partially created.

### 7.1. Relationship between ticket types

The design must use object-oriented inheritance mechanisms, through class extension and/or interface implementation, to represent the common behavior of the different ticket types. Individual and group tickets may not be implemented as two entirely independent classes that duplicate common logic. In particular, price-related behavior and elements common to all ticket types must be reused. The design must allow different types of ticket to be handled through a common abstraction when an operation does not need to know the concrete type. Choosing a base class, an abstract class, an interface, or a combination of these mechanisms is part of the design to be carried out by the student.

### 7.2. Individual ticket

An individual ticket will be associated with a single user. The creation command will be:

TICKET CREATE;<identifier>;<email>;<date>

For example:

```text
TICKET CREATE;T001;ana@correo.com;2027-04-15
```

The identifier must be unique among all tickets in the system. The user must already exist in the system. The specified date must be equal to or later than the current system date. Tickets may not be created for past dates. The ticket will be valid only on the date specified at creation. The price of a new ticket will be the current base price configured in the system. If SYSTEM PRICE has not been used during the execution, the initial price of 40.00 euros will apply. When a ticket is successfully created, the application must display the price that will be charged for it. An individual ticket must hold a reference to the user for whom it was purchased. This relationship is unidirectional: the ticket knows the user, but the user must not maintain references to their tickets. An individual ticket may be deleted using:

TICKET DELETE;<identifier>

Deletion is allowed only when the ticket date is strictly later than the current system date. Tickets for the current day or earlier dates may not be deleted. Such tickets must be retained as historical records. Individual tickets belonging to the composition of a group ticket must not be deleted independently. Their life cycle depends on the group ticket containing them.

### 7.3. Group ticket

A group may purchase a joint ticket for all users who belong to it at that moment using:

GROUPTICKET CREATE;<identifier>;<group>;<date>

For example:

```text
GROUPTICKET CREATE;TG01;G01;2027-04-15
```

The identifier must be unique among all tickets in the system. The specified date must be equal to or later than the current system date; group tickets may not be created for past dates. A group must contain at least one user before a group ticket can be created. Empty groups may be created and populated progressively, but a group ticket may not be purchased while the group is empty. A group ticket must be composed of individual tickets, one for each user belonging to the group at purchase time. These individual tickets constitute the composition of the group ticket and must not be shared with other group tickets. The identifier of each individual ticket created as part of the composition will be generated automatically using:

<groupTicketIdentifier>:<dni>

For example, for a group ticket identified as TG01 and a user with DNI 12345678Z, the corresponding individual ticket will have the identifier:

```text
TG01:12345678Z
```

These derived identifiers belong to the same shared ticket identifier space and must be checked before group ticket creation is completed. Individual tickets belonging to a group ticket may not be deleted directly using TICKET DELETE. They may only be deleted as a consequence of valid deletion of the containing group ticket using GROUPTICKET DELETE. Each individual ticket comprising a group ticket will hold a reference to the corresponding user. The group ticket must not maintain a parallel collection of users duplicating this information. The base price used to create individual tickets will be the current price configured in the system. A discount based on the number of members included in the purchase will be applied to that price. Once the group ticket is successfully created, the application must display the total purchase price after applying the corresponding discount. The composition created at purchase time must not subsequently change, even if the group’s state changes. A group ticket must hold a reference to the group that made the purchase while that group exists in the system. This relationship is unidirectional: the group ticket knows its group, but the group must not hold references to purchased tickets.

If the group is subsequently deleted under the established rules, the reference held by historical group tickets may become null. Similarly, users must not hold references to their tickets. Whenever it is necessary to determine the tickets associated with a user or group, this information must be obtained by traversing the tickets managed by the system. A group ticket may be deleted using:

GROUPTICKET DELETE;<identifier>

Deletion is permitted only when the group ticket date is strictly later than the current system date. Group tickets for the current day or earlier dates may not be deleted and must be retained as historical records. When a future group ticket is deleted, the individual tickets in its composition must also be deleted.

## 8. Group discounts

The applicable discount depends on the number of users included in the group ticket when it is created. The following brackets apply:

| Number of members | Discount |
| --- | --- |
| Fewer than 3 | 0% |
| 3 to 5 | 10% |
| 6 to 10 | 20% |
| More than 10 | 50% |

The final price must be calculated by reusing the common behavior defined for tickets and applying the rules specific to group tickets. The discount will be applied to the base price of each individual ticket in the group ticket. The total group ticket price may be obtained from the prices of its constituent individual tickets. For example, if the current system price is 40 euros and a group of 6 users creates a group ticket:

```text
GROUPTICKET CREATE;TG02;G02;2027-04-15
```

a discount of 20% will be applied. Each of the six individual tickets in the group ticket will cost 32 euros, for a total of 192 euros. In this case, the application must display a total charge of 192 euros. As long as any associated active group ticket exists, the group composition will remain locked against modification. Once all associated tickets are historical or have been validly deleted, the group may be modified again.

## 9. Relationship between users and tickets

A ticket is considered active when its date is equal to or later than the current system date. Tickets with earlier dates are considered historical. From this delivery onward, USER DELETE, defined in Phase 1, must take account of existing tickets. A user may not be deleted while any active ticket is associated with them. This restriction applies both to individual tickets created using TICKET CREATE and to individual tickets comprising a group ticket. Historical tickets alone will not prevent deletion of the user. A user’s locked state must not be stored as an independent attribute, but derived from existing tickets and the current system date. If the user only has future tickets, those tickets may first be deleted through the corresponding deletion operations. Tickets for the current day may not be deleted and will continue to block USER DELETE. Users must not store their own tickets. To determine a user’s tickets, the information must be obtained from the tickets managed by the system. When deleting a user is permitted, the system must remove that user from the groups they belong to in order to maintain model consistency. However, USER DELETE may not be performed if the user belongs to a group locked by an associated active group ticket. Deleting the user would indirectly modify the composition of that group and must therefore respect the same restrictions that prevent GROUP ADD or GROUP REMOVE when an active group ticket exists. If all groups to which the user belongs can be modified, their removal from those groups will occur as an internal consequence of USER DELETE. Historical group tickets will preserve the composition they had at purchase time. Deleting a user must not invalidate the historical information of tickets with dates earlier than the current date. Deletion changes the user’s status as an active system user, but historical tickets must be retained as fiscal records. Persistence must preserve the minimum information needed to correctly reconstruct those tickets even if the user no longer exists as an active user. Likewise, deleting a group must not invalidate historical group tickets with earlier dates. When a group is deleted, its associated historical group tickets must be retained as fiscal records. The group reference may become null, while the group ticket retains the information needed to preserve that historical record, including its identifier, date, price, and composition.

## 10. Access to attractions

Attractions will be accessed using a ticket identifier:

ATTRACTION ENTER;AttractionIdentifier;TicketIdentifier

For example:

```text
ATTRACTION ENTER;A01;T001
ATTRACTION ENTER;A01;TG01
```

The ticket must exist and be valid for the current system date. Its date will be checked only when entering the attraction. Once entry has occurred, the user’s presence in the attraction will not depend on subsequent changes to the system date. If an individual ticket is used, the user associated with it will enter the attraction. If a group ticket is used, all users associated with the individual tickets in its composition will enter together. The attraction must have enough capacity for everyone who needs to enter. Access using a group ticket is indivisible: if capacity is insufficient for all users, none may enter. The operation must take advantage of the common abstraction shared by ticket types and avoid maintaining completely separate access mechanisms.

## 11. Leaving attractions

A user leaves an attraction using:

ATTRACTION EXIT;AttractionIdentifier;Email

For example:

```text
ATTRACTION EXIT;A01;ana@correo.com
```

The operation must remove the specified user from the attraction’s occupant collection and release the corresponding capacity. When several users entered with a group ticket, each may subsequently leave the attraction using their own email address. Users must not store references to attractions they are in.

## 12. Checking attraction status

The application must allow the current status of an attraction to be checked using:

ATTRACTION STATUS;AttractionIdentifier

For example:

```text
ATTRACTION STATUS;A01
```

The operation must display at least:

- attraction identifier;
- name;
- maximum capacity;
- number of users currently inside;
- number of available places;
- users currently inside.

The information must be obtained from the state maintained by the attraction itself. The result must be independent of the way users entered. Once inside, all occupants must be treated as present users, whether they entered with individual or group tickets. Students may decide the exact command output provided that it is understandable and includes all required information.

## 13. Persistence

The addition of groups, tickets, and attractions extends the state that the application must preserve between runs. The solution must maintain the separation of responsibilities introduced in the first delivery. Data must be stored in text files and correctly reconstructed when the application starts again. Students must decide how to organize persistence of new elements and their relationships. The data needed to reconstruct the following must be preserved:

- groups and their users;
- individual tickets and their user;
- group tickets, their constituent individual tickets, and, while the group exists, the reference to the group that made the purchase;
- attractions.

The collection of users currently inside each attraction will not be persisted. At the start of a new execution, all attractions must be empty, regardless of their state when the previous execution ended. This extension may not be implemented through automatic Java object serialization. Databases, persistence frameworks, and external libraries are not permitted.

### 13.1. Temporary persistence mode

The application must support an optional temporary execution mode intended to facilitate testing without modifying the persistent data from a normal execution. When the JAR is run with the argument:

```text
--fly
```

at startup, the application must create an independent temporary directory identified by a timestamp. For example:

```text
tmp/20260826_190315/
```

During that execution, all repositories must use only files located inside that temporary directory. Temporary mode must cover all persistent system elements, including users, groups, tickets, and attractions. Repositories must not have an alternative implementation specific to this mode. The difference between normal and temporary persistence must be handled through configuration of repository paths. When execution ends, the created temporary directory and all its files must be deleted. This cleanup must occur both when the application ends through EXIT and when processing of a command file finishes normally. The --fly mode must be usable both interactively and with a command file. This feature extends the execution modes established in Phase 1. Without --fly, argument behavior must remain exactly as in the previous delivery. With --fly, it appears as the first argument and may optionally be followed by a command file path. Accordingly, the following forms of execution must be supported:

```text
java -jar target/nombre-aplicacion.jar
java -jar target/nombre-aplicacion.jar input_fase2.txt
java -jar target/nombre-aplicacion.jar --fly
java -jar target/nombre-aplicacion.jar --fly input_fase2.txt
```

When --fly is not used, the application must retain its normal permanent-persistence behavior. The purpose of this mode is to enable isolated, repeatable executions without altering the persistent state used by other executions.

```text

```

The PlantUML diagram must represent the model structure and relationships among its elements. Methods and constructors need not be included. Only relevant attributes and, where appropriate to the design, the following must be shown:

- classes and interfaces;
- relevant enumerations;
- inheritance;

In particular, the ticket hierarchy, composition between a group ticket and its individual tickets, and the relationships among users, groups, tickets, and attractions must be represented correctly. ## 16. Technical restrictions

Delivery 2 must retain all the technical requirements established in previous phases.

The project must continue to use Java 21 and Maven and generate, using mvn package, an executable JAR that can be run interactively or with a command file. Databases, persistence frameworks, and external libraries are not permitted. Relationships between objects must be represented with objects and collections while those elements are loaded into memory; domain relationships must not be unnecessarily replaced by identifiers or strings. Relationships must respect the directions specified in this document:

- attractions know which users are inside them, but users do not know the attractions;
- individual tickets know the user for whom they were purchased, but users do not store their tickets;
- group tickets are composed of the individual tickets of users included in the purchase;
- group tickets hold a reference to the purchasing group while it exists; this reference may become null when the group is deleted;
- groups and users do not store references to purchased tickets.

The different ticket types must be part of a common abstraction through class extension and/or interface implementation. The design must reuse shared information and behavior, particularly price-related behavior. Group tickets must use composition to contain the individual tickets representing their members. A solution implementing each ticket type completely independently, without object-oriented inheritance or abstraction mechanisms, will not be considered valid. The system must use a single instance of the element responsible for central park management. Tickets for the current day or earlier dates may not be deleted through ticket deletion commands and must be preserved in the system’s historical record. The --fly execution mode must reuse the same repositories and persistence mechanisms as normal execution, changing only the paths used to store data. Phase 1 features may not be removed or replaced with features incompatible with the previous specification.

## 17. Mandatory Git roadmap

Development of the second delivery must continue incrementally in the same repository used in Phase 1. Each of the following milestones must correspond to a functional, coherent state of the project. The specified messages are mandatory and must be used exactly as written. Additional commits may be made between mandatory milestones.

### 17.1. F2-C01 — Central management and system date

The application must incorporate the element responsible for maintaining and coordinating the overall park state, including the current date and current base ticket price. The initial date will be the local date when execution starts, and the initial price will be 40.00 euros. The SYSTEM DATE and SYSTEM PRICE commands must be available.

```text
[F2-C01] Add park controller and system date
```

### 17.2. F2-C02 — Adding groups

The system must allow groups to be created with an identifier and name, even if initially empty, and users to be added or removed while the group can be modified. The same user may not appear more than once in the same group.

```text
[F2-C02] Add user groups
```

### 17.3. F2-C03 — Adding individual tickets

The common ticket abstraction and individual ticket creation through TICKET CREATE must be added, using the current system price and rejecting dates earlier than the current date. This milestone must also add TICKET DELETE, allowing deletion only of tickets dated strictly after the current date. From this milestone onward, USER DELETE must also inspect existing individual tickets and reject deletion if a user has a ticket dated on or after the current system date.

```text
[F2-C03] Add individual tickets
```

### 17.4. F2-C04 — Group tickets

Nonempty groups may create tickets through GROUPTICKET CREATE, provided the specified date is not in the past. The group ticket must be composed of the individual tickets of the members included in the purchase. Their identifiers will be generated automatically using <groupTicketIdentifier>:<dni>. The group ticket must also maintain a reference to the purchasing group while it exists in the system and use the current system price as the basis for the applicable discount. This milestone must also add GROUPTICKET DELETE and GROUP DELETE. A group ticket may be deleted only when its date is strictly later than the current date. GROUP ADD, GROUP REMOVE, and GROUP DELETE must check whether associated active group tickets exist. The USER DELETE check must also cover individual tickets belonging to active group tickets and prevent deletion when it would modify a locked group.

```text
[F2-C04] Add group ticket purchase
```

### 17.5. F2-C05 — Adding attractions

The park must support attractions with an identity, name, capacity, and occupant collection. ATTRACTION LIST must also be added to view the users currently inside an attraction.

```text
[F2-C05] Add attractions
```

### 17.6. F2-C06 — Individual attraction access

Individual tickets may be used with ATTRACTION ENTER to access an attraction.

```text
[F2-C06] Add individual attraction access
```

### 17.7. F2-C07 — Access using group tickets

The same access operation must support group tickets atomically while respecting the attraction capacity. Consulting attraction status must allow the results of entry and exit operations to be verified.

```text
[F2-C07] Add group attraction access
```

### 17.8. F2-C08 — Complete park persistence

The application must be able to terminate and later reconstruct the required park state, including the new elements and their relationships. This milestone must also add temporary --fly persistence mode, using the same repositories configured to use an independent temporary directory that must be deleted at the end of execution.

```text
[F2-C08] Extend park persistence
```

### 17.9. F2-C09 — UML model

The resulting design must be documented using PlantUML, following the rules specified in this document.

```text
[F2-C09] Add PlantUML class model
```

### 17.10. F2-C10 — Delivery 2 integration

All previous features must work together and commands from both deliveries must coexist correctly.

```text
[F2-C10] Complete delivery 2 integration
```
