# F3 — Amusement Park | Comprehensive OpenSpec Change Brief

> **Change intent:** Evolve the existing Java 21 / Maven amusement-park application from Deliveries 1 and 2 by implementing all ten Delivery 3 milestones as **one OpenSpec change**. Preserve earlier behavior except where this source explicitly changes it.
>
> **Source of truth:** The full uploaded F3 proposal is reproduced verbatim in Appendix A. Its concrete requirements and mandatory commit strings govern any detail not exhaustively restated below. The structured text before the appendix is an improved planning interpretation, not a replacement for the source.

## 1. Why

The application already supports users, groups, tickets, attractions, command processing, and normal/temporary persistence. Delivery 3 must strengthen architecture, security, extensibility, domain behavior, and integration without breaking earlier features. Spec-first planning will make the changes traceable and testable across the complete delivery.

## 2. What changes

This single change encompasses all ten source milestones (F3-C01 through F3-C10), in that order:

| Milestone | Capability / outcome | Nature |
|---|---|---|
| F3-C01 | `layered-application` — presentation/business/persistence packages | Modify architecture |
| F3-C02 | `invoice-generation` — user/group invoices with Builder | Add behavior |
| F3-C03 | `controller-lifecycle` — Singleton controllers and injected dependencies | Modify architecture |
| F3-C04 | `extended-command-help` — HELP EXTENDED and injected help generation | Extend behavior |
| F3-C05 | `password-security` — BCrypt for persisted passwords | Modify behavior |
| F3-C06 | `personal-passes` — SpeedPass and Special Pass purchases/refunds | Add behavior |
| F3-C07 | `attraction-ticket-typing` — interfaces and bounded generics | Modify domain/access typing |
| F3-C08 | `pass-based-entry` — entry/consumption checks and atomic access | Extend behavior |
| F3-C09 | `delivery3-persistence-and-uml` — persisted pass/type state and accurate UML | Extend persistence/docs |
| F3-C10 | `delivery3-integration` — fully functional executable across modes | Verify integration |

**In scope:** Source-listed domain rules, CLI commands, layered restructuring, dependency injection, Builder, BCrypt dependency, passes, attraction typing, transactional-style all-or-nothing state changes, file persistence, PlantUML, regression tests, executable JAR, and required milestone commits.

**Out of scope:** A new graphical or HTTP interface; a database; a dependency-injection framework; redesign of E1/E2 commands not required by F3; automatic migration of earlier plaintext files unless separately specified; additional commercial features or novel access policies.

**Compatibility:** E1 and E2 command formats and execution modes must remain functional, with the listed F3 extensions. Decisions must be derived from existing repository behavior and authoritative earlier specs rather than invented.

## 4. Capability requirements and acceptance scenarios

The following numbered requirements and scenarios make the source testable; retain the original text in Appendix A for further detail.

### 4.1 `layered-application` — F3-C01

**Requirements**

- **LAY-01:** The application SHALL physically organize Java code into distinct `presentation`, `business`, and `persistence` packages; it SHALL NOT use the default package.
- **LAY-02:** Presentation SHALL own command interaction and SHALL NOT access persistence files directly.
- **LAY-03:** Domain objects SHALL NOT directly read or write persisted files; repositories/file I/O SHALL remain in persistence.
- **LAY-04:** All E1/E2 command syntax and observable results SHALL remain operational, and `mvn package` SHALL build the project.

**Scenarios**

- **Given** the refactored source tree, **when** package dependencies are inspected, **then** all three packages exist with the specified responsibility boundaries and no default-package classes.
- **Given** representative E1/E2 commands, **when** executed before and after reorganization, **then** their functional behavior remains equivalent.
- **Given** the repository, **when** `mvn package` runs, **then** it generates the executable JAR.

### 4.2 `invoice-generation` — F3-C02

**Requirements**

- **INV-01:** The application SHALL generate user and group invoices on demand using `INVOICE CREATE;USER;<correo>` and `INVOICE CREATE;GROUP;<identificadorGrupo>`.
- **INV-02:** Invoice construction SHALL explicitly use a Builder abstraction and distinct assembly steps, including only applicable nonempty sections and avoiding constructors with numerous optional fields.
- **INV-03:** A user invoice SHALL account for directly purchased individual tickets and eligible personal passes, but SHALL NOT double-count individual tickets composing group tickets.
- **INV-04:** A group invoice SHALL include its group-ticket purchases and amounts, but SHALL NOT count constituent tickets or members' personal passes again.
- **INV-05:** Invoices SHALL show relevant item prices and totals, and SHALL NOT require persistence.

**Scenarios**

- **Given** an existing user with directly bought tickets and personal passes, **when** a user invoice is requested, **then** it shows applicable purchases and their amounts, without double-counting constituent tickets.
- **Given** an existing group with group-ticket purchases, **when** a group invoice is requested, **then** it includes the group-ticket totals, excludes personal passes, and calculates the stated total correctly.
- **Given** an invoice category with no applicable items, **when** the invoice is assembled, **then** the irrelevant section is omitted.

**Sequencing note:** F3-C02 is specified before passes are introduced at F3-C06. Implement the Builder and currently available ticket sections first; when F3-C06 is implemented, complete personal-pass inclusion without deviating from the source milestone order. Keep this dependency visible in design/tasks.

### 4.3 `controller-lifecycle` — F3-C03

**Requirements**

- **CTL-01:** Controllers representing a unique management responsibility SHALL enforce one instance within an execution using the Singleton pattern.
- **CTL-02:** Repositories SHALL remain replaceable, configurable dependencies; they SHALL NOT be made global Singletons solely because a controller uses them.
- **CTL-03:** Repository and inter-controller/service dependencies SHALL be created/configured at application startup and injected, rather than instantiated inside the business operation that uses them.
- **CTL-04:** Normal and `--fly` modes SHALL select different repository paths without changing controller business logic.

**Scenarios**

- **Given** repeated requests for a unique controller within one execution, **when** it is accessed, **then** the same instance is used.
- **Given** normal and fly-mode startup, **when** repositories are wired, **then** controllers receive correctly configured instances and the domain operations do not require mode-specific implementations.

### 4.4 `extended-command-help` — F3-C04

**Requirements**

- **HLP-01:** `HELP` SHALL continue displaying concise command syntax.
- **HLP-02:** `HELP EXTENDED` SHALL display each registered command's syntax and a brief description.
- **HLP-03:** The help-generation class SHALL receive its output-building behavior through dependency injection; command execution SHALL NOT be coupled to a particular future help format.

**Scenarios**

- **Given** known commands, **when** `HELP` runs, **then** concise syntax is displayed.
- **Given** the same command registry, **when** `HELP EXTENDED` runs, **then** syntax plus descriptions appear.
- **Given** an alternative help renderer injected at startup, **when** help is generated, **then** command processing requires no direct construction of that renderer.

### 4.5 `password-security` — F3-C05

**Requirements**

- **SEC-01:** The project SHALL include a Maven dependency supporting BCrypt password hashing.
- **SEC-02:** Newly stored passwords SHALL be protected as BCrypt hashes, not plaintext; existing E1 password-format validation SHALL happen before hashing.
- **SEC-03:** `USER DELETE` and `USER UPDATE` SHALL verify the supplied password against the stored protected value.
- **SEC-04:** A changed password SHALL produce and persist a new BCrypt protected value.

**Scenarios**

- **Given** a valid new password, **when** a user is created, **then** the stored representation does not contain its plaintext password.
- **Given** a correct/incorrect password, **when** a delete or update is requested, **then** verification respectively permits/rejects the operation.
- **Given** a password change, **when** persistence is inspected and the application restarts, **then** a protected new value is stored and usable for later authentication.

### 4.6 `personal-passes` — F3-C06

**Requirements**

- **PASS-01:** Passes SHALL be associated with individual tickets. Each SHALL carry its own identity, purchase price and consumption state.
- **PASS-02:** `SPEEDPASS CREATE` SHALL support quantities **1** and **10**, producing separate SpeedPass objects. Each SpeedPass SHALL cost **20%** of the associated ticket's stored price.
- **PASS-03:** `SPECIALPASS CREATE` SHALL permit at most one Special Pass per individual ticket throughout its lifetime, at a price equal to that ticket's stored price.
- **PASS-04:** Purchase operations SHALL display the amount charged. Consumed passes SHALL remain recorded, and only eligible unused passes SHALL be refundable through the corresponding DELETE commands under E2 date constraints.

**Scenarios**

- **Given** an eligible ticket, **when** ten SpeedPasses are purchased, **then** ten distinct passes exist with the correct individual/total price and initial state.
- **Given** an individual ticket that has ever acquired a Special Pass, **when** another is requested, **then** it is rejected even if the first pass was consumed.
- **Given** an unused eligible pass versus a consumed pass, **when** refund is requested, **then** only the eligible unused pass may be removed.

### 4.7 `attraction-ticket-typing` — F3-C07

**Requirements**

- **TYPE-01:** Attraction types SHALL include `GENERAL`, `INDIVIDUAL`, `GROUP`, and `SPECIAL`.
- **TYPE-02:** Ticket access capabilities SHALL be represented by interfaces, and attractions SHALL use functionally meaningful bounded generic types to constrain admitted ticket classes.
- **TYPE-03:** `GENERAL` SHALL admit individual/group tickets; `INDIVIDUAL` individual tickets only; `GROUP` group tickets only; `SPECIAL` individual tickets with separate pass requirements applied by its own behavior.
- **TYPE-04:** Existing E2 attraction creation without an explicit type SHALL continue to create `GENERAL` attractions; the expanded syntax SHALL accept an explicit type.

**Scenarios**

- **Given** the old attraction-create command, **when** executed, **then** a GENERAL attraction is created.
- **Given** each typed attraction, **when** compatible/incompatible ticket forms are used, **then** the correct acceptance or rejection occurs.
- **Given** source code generic declarations, **when** inspected, **then** their bounds enforce meaningful ticket-access restrictions rather than unused type parameters.

### 4.8 `pass-based-entry` — F3-C08

**Requirements**

- **ENTRY-01:** Existing `ATTRACTION ENTER;<atraccion>;<entrada>` SHALL remain valid; the optional `;SPEED` suffix SHALL request SpeedPass entry where permitted.
- **ENTRY-02:** A successful individual SPEED entry SHALL consume exactly one available SpeedPass and report the consumed pass; failures SHALL consume none.
- **ENTRY-03:** A group SPEED entry at a GENERAL or GROUP attraction SHALL verify all members' passes and all ordinary access constraints before any modification; success SHALL admit the complete group and consume one SpeedPass per member, while failure SHALL alter neither occupancy nor passes.
- **ENTRY-04:** SPECIAL attractions SHALL automatically require and consume an unused Special Pass for individual entry, SHALL report it, and SHALL reject `SPEED`.

**Scenarios**

- **Given** one ticket with multiple unused SpeedPasses, **when** eligible SPEED entry succeeds, **then** exactly one becomes consumed and its identifier is reported.
- **Given** a group where one member lacks an unused SpeedPass, **when** group SPEED entry is requested, **then** no member enters and no pass is consumed.
- **Given** an individual ticket with an unused Special Pass, **when** special-attraction entry succeeds, **then** the pass is consumed automatically; **when** `SPEED` is provided, **then** access is rejected.

### 4.9 `delivery3-persistence-and-uml` — F3-C09

**Requirements**

- **PST-01:** Persistence SHALL reconstruct each pass, its price, individual ticket association, and consumption status, and each attraction's type.
- **PST-02:** Valid deletion of a future individual ticket SHALL cascade-delete all associated passes.
- **PST-03:** Valid deletion of a future group ticket SHALL consistently remove constituent passes, individual tickets, then the group ticket; a failure SHALL NOT leave partially deleted state.
- **PST-04:** `--fly` SHALL isolate all new persistent F3 data just as it isolates E2 data.
- **PST-05:** `uml/model.puml` SHALL be updated to reflect the actual F3 implementation, including relevant classes, interfaces, generics and relationships.

**Scenarios**

- **Given** stored passes and typed attractions, **when** the application restarts, **then** their associations, amounts, states and types are reconstructed.
- **Given** an eligible future ticket with passes, **when** deletion succeeds, **then** all its dependent entities are removed consistently; **when** a precondition fails, **then** no partial deletion is left.
- **Given** `--fly`, **when** F3 data is written and the run ends, **then** normal persistent files remain unchanged.
- **Given** `uml/model.puml`, **when** compared with the final code, **then** represented relationships and types match the implementation.

### 4.10 `delivery3-integration` — F3-C10

**Requirements**

- **INT-01:** All E1/E2 and F3 commands SHALL coexist in one command-processing system, preserving interaction and execution from command files.
- **INT-02:** `HELP` and `HELP EXTENDED` SHALL include all new supported commands.
- **INT-03:** Both normal and `--fly` persistence SHALL function correctly for the full F3 state.
- **INT-04:** `mvn package` SHALL generate a working executable JAR and the final UML SHALL correspond to the implementation.

**Scenarios**

- **Given** an end-to-end scenario spanning older and newer commands, **when** run interactively or through an input file, **then** the same domain outcomes are produced.
- **Given** normal and temporary execution modes, **when** the same business scenarios run, **then** business outcomes agree while persistence locations remain isolated.
- **Given** the finished code, **when** Maven tests/package and OpenSpec validation run, **then** they succeed and the documented design matches implementation.

## 5. Design decisions to record, not invent

Before implementation, examine the earlier specs and actual code and document:

1. **Invoice sequencing:** The invoice milestone precedes pass creation. State how the later pass section integrates without fictional pass objects at F3-C02.
2. **Repository configuration and Singleton lifecycle:** Explain how per-run unique controllers receive replaceable repositories across normal and `--fly` execution without relying on global repository Singletons.
3. **Pass identifier and date rules:** Reuse the explicit F3 source and authoritative earlier specification for exact command arguments and date boundaries; do not extrapolate new rules from examples alone.
4. **Persistence consistency:** Define preflight checks and safe writes that ensure cascade deletion is not partially persisted.
5. **E1/E2 compatibility:** Document how protected passwords relate to existing user files; do not silently impose backward migration.
6. **Generic access:** Show the interface bounds, real ticket capabilities, and attraction-specific eligibility checks with no decorative type parameters.
7. **Testing ambiguity:** If an earlier authoritative document specifies behavior not completely defined by this brief, reference it directly. If a true conflict exists, mark it for human decision before coding.
