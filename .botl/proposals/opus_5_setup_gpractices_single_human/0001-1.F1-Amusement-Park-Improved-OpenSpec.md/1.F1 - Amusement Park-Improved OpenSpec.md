# F1 — Amusement Park: Project Setup, User Management, and Command Execution

## OpenSpec change request

**Change ID suggestion:** `implement-f1-amusement-park`  
**Change type:** Initial application / Delivery 1  
**Target stack:** Java 21, Maven, Maven Quickstart archetype, Java standard library  
**Source of truth:** The complete original request in the appendix is authoritative; the structured requirements below organize it for implementation without intentionally changing its scope.

### Why

Establish an independently runnable Java application, then introduce persistent user management and a consistent text-command interface that works from the terminal or a command file. This creates the foundation for later amusement-park features without implementing them prematurely.

### What changes

1. Bootstrap a Maven Quickstart project on JDK 21 with a runnable main class, executable JAR, and basic testing infrastructure.
2. Introduce a properly encapsulated user model, validation rules, unique identity constraints, user creation/deletion/update operations, and text-file persistence.
3. Introduce a shared command-processing path for interactive and file modes, with `HELP`, `EXIT`, and controlled handling of invalid commands and unreadable files.

### Scope and exclusions

**In scope:** Project initialization, Java/Maven build and testing, executable JAR, user commands and their exact input formats, Spanish DNI validation, email/password/card validation, user uniqueness, text-file persistence, interactive/file command execution, `HELP`, `EXIT`, and regression testing.

**Out of scope:** Attractions, groups, tickets, passes, encryption, databases, persistence frameworks, third-party libraries, regular expressions, advanced architectural layers, and design patterns introduced solely for later phases. Do not expand the application beyond these capabilities.

### Implementation sequence

Organize the implementation into three incremental stages **inside this single OpenSpec change**, keeping the project buildable and tested at each stage:

1. **Bootstrap:** Maven Quickstart/JDK 21, main entry point, executable JAR, base tests; no domain features yet.
2. **User management:** User model, validation, commands, persistence, and create/delete/update operations.
3. **Execution and control:** Shared interactive/file input handling, `HELP`, `EXIT`, and input/file error handling.

Do not treat the stages as independent replacements: each stage must preserve behavior from the previous one. The specification and task plan should make the dependency order explicit.

## Requirements and acceptance scenarios

The statements below use **SHALL** to express required behavior. Translate them into OpenSpec capability specifications with verifiable scenarios. Examples are illustrative input/output constraints from the source, not permission to invent extra features.

### Capability A — Java project and runnable packaging

**A1.** The project SHALL use **JDK 21** and **Maven**, preserving the standard structure generated by `org.apache.maven.archetypes:maven-archetype-quickstart`.

**A2.** The project SHALL have an application entry-point class and the basic testing structure. `mvn test` SHALL complete successfully.

**A3.** The build SHALL generate an **executable JAR** whose entry point invokes the application. Project bootstrap SHALL not add application-domain functionality before the user-management stage.

**Scenario: clean project build**
- **Given** the project has been checked out in a compatible JDK 21 environment
- **When** `mvn test` runs
- **Then** the project compiles and its tests pass.

**Scenario: executable entry point**
- **Given** a packaged application
- **When** its executable JAR is launched
- **Then** the application enters the supported command-execution path rather than requiring an IDE.

### Capability B — User model and responsibilities

**B1.** Each user SHALL hold first name, surname(s), DNI, email address, password, telephone number, and card number. All attributes SHALL be encapsulated, and DNI SHALL remain immutable after creation.

**B2.** Separate classes SHALL be responsible, at minimum, for (a) representing users, (b) starting the application and terminal interaction, and (c) saving/loading users. Neither the user model nor the main application class SHALL directly implement text-file reading/writing.

**Scenario: immutable DNI**
- **Given** an existing user
- **When** an update is requested
- **Then** the user's DNI cannot be changed through `USER UPDATE`.

**Scenario: responsibility separation**
- **Given** the implementation
- **When** the project structure is inspected
- **Then** domain representation, application entry/interaction, and persistence responsibilities are in distinct classes.

### Capability C — User creation and input validation

**C1.** Commands SHALL be parsed from semicolon-delimited text using Java `String.split` and other basic `String` operations, without external command-parsing libraries. The user commands SHALL include `USER CREATE`, `USER DELETE`, and `USER UPDATE`.

**C2.** The application SHALL accept the creation syntax, preserving the parameter order:

```text
USER CREATE;Nombre;Apellidos;DNI;Correo;Contraseña;Telefono;Tarjeta
```

**C3.** The application SHALL validate all required user data before storing a new user and SHALL reject invalid user creation without persisting a partial user.

**C4.** The DNI SHALL consist of eight digits and the correct final letter according to the standard Spanish DNI algorithm; format-only checks SHALL NOT suffice.

**C5.** The email address SHALL be validated using basic `String` operations, not regex. The required pattern is `texto@texto.xxx`: nonempty local part, nonempty domain, a period after `@`, and an extension of **exactly three characters**.

**C6.** A password SHALL contain at least one uppercase letter, one lowercase letter, one digit, and one symbol. Neither regular expressions nor third-party libraries SHALL be used for this check.

**C7.** The card number SHALL contain exactly 16 consecutive digits with no whitespace, letters, or symbols. The telephone number SHALL be stored without additional transformation.

**C8.** No two registered users SHALL share a DNI or email address.

**Scenario: valid registration**
- **Given** there is no registered user with DNI `12345678Z` or email `ana@correo.com`
- **When** `USER CREATE;Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1!;612345678;1234567890123456` is processed
- **Then** the user is created and stored.

**Scenario: DNI checksum, not just shape**
- **Given** an otherwise valid user request
- **When** the DNI is `12345678A`
- **Then** creation is rejected; `12345678Z` satisfies the stated DNI example.

**Scenario: email extension length**
- **Given** an otherwise valid registration
- **When** the email is `ana@correo.es`
- **Then** creation is rejected because the extension has two characters.

**Scenario: password and card validation**
- **Given** a new user request
- **When** its password lacks any required character category, or its card contains spaces or a length other than 16 digits
- **Then** creation is rejected without persisting that user.

**Scenario: duplicate identifiers**
- **Given** an existing user with DNI `12345678Z` and email `ana@correo.com`
- **When** another user is created with either the same DNI or the same email
- **Then** creation is rejected.

### Capability D — User persistence

**D1.** The application SHALL store users in a **semicolon-separated text file**, with one user per line and attributes in the specified order. It SHALL load previously stored users at startup.

**D2.** A class separate from both the user model and main class SHALL read and write persistent user data. No database or external persistence library SHALL be used.

**Scenario: restart restores users**
- **Given** a valid user was created during one execution
- **When** the application terminates and starts again
- **Then** the user is reconstructed from the text file with the saved attributes.

**Scenario: persisted updates and deletions**
- **Given** a previously stored user
- **When** a valid update or deletion is performed and the application restarts
- **Then** the file-backed state reflects that operation.

### Capability E — User deletion and updates

**E1.** Deletion SHALL use:

```text
USER DELETE;Correo;Contraseña
```

The system SHALL locate the user by current email, validate the supplied password, delete only on successful authentication, and update persistent storage.

**E2.** Updates SHALL use:

```text
USER UPDATE;Correo;Contraseña;Campo;NuevoValor
```

The current email and password SHALL be checked before any modification.

**E3.** Updatable fields SHALL be represented by an `enum` covering `NAME`, `SURNAME`, `EMAIL`, `PASSWORD`, `PHONE`, and `CARD`. DNI SHALL NOT be editable. Replacement values SHALL satisfy the corresponding creation-time validation and uniqueness constraints, and successful changes SHALL persist.

**Scenario: authenticated deletion**
- **Given** an existing user with known credentials
- **When** `USER DELETE` receives matching email and password
- **Then** the user is deleted and persistence is updated.

**Scenario: wrong credentials**
- **Given** an existing user
- **When** `USER DELETE` or `USER UPDATE` receives an incorrect current password or a nonexistent email
- **Then** the operation makes no change.

**Scenario: email update uniqueness**
- **Given** two different registered users
- **When** one user attempts to update their email to that of the other
- **Then** the update is rejected.

**Scenario: password/card revalidation**
- **Given** an existing user with valid current credentials
- **When** an update supplies a password failing the character rules or a card failing the 16-digit rule
- **Then** the update is rejected and the original state remains intact.

### Capability F — Interactive/file command execution

**F1.** When launched without arguments, the application SHALL read **one command per input line** from standard input until `EXIT` or end-of-input.

**F2.** When supplied with a file path as its first execution argument, the application SHALL read that file line by line and process nonempty commands **in order**. Blank lines SHALL be ignored.

**F3.** Interactive and file modes SHALL invoke the **same command interpretation and execution logic**; they SHALL NOT duplicate the individual command implementations.

**F4.** An invalid command or insufficient parameters SHALL NOT cause unexpected application termination. Unavailable, unreadable, or invalidly opened input files SHALL produce controlled error handling rather than an uncaught exception presented to the user.

**Scenario: equal behavior across input modes**
- **Given** the same valid command sequence and equivalent initial persistent state
- **When** the sequence is supplied interactively or through a command file
- **Then** the observable results of each command are equivalent.

**Scenario: ordered file processing**
- **Given** a file with valid commands and blank lines
- **When** file mode executes
- **Then** the nonblank commands are executed in file order, and blanks do not cause errors.

**Scenario: invalid input is recoverable**
- **Given** an active interactive session
- **When** malformed or unknown command text is entered
- **Then** the application handles it without terminating unexpectedly and remains able to process subsequent input.

### Capability G — HELP and EXIT

**G1.** `HELP` SHALL display the available commands and their basic syntax, including `USER CREATE`, `USER DELETE`, `USER UPDATE`, `HELP`, and `EXIT`. Its description SHALL remain consistent with the operations actually implemented.

**G2.** `EXIT` SHALL end interactive execution in a controlled manner and SHALL stop command-file processing immediately, leaving any later file commands unexecuted.

**Scenario: help lists current commands**
- **Given** the completed F1 application
- **When** `HELP` is executed
- **Then** the five specified commands and their basic syntax are shown.

**Scenario: no commands after EXIT**
- **Given** a file containing `USER CREATE`, then `EXIT`, then another `USER CREATE`
- **When** file mode runs
- **Then** only the first creation is eligible for execution and the later creation is not executed.

## Design guidance for OpenSpec

Document only design choices that materially affect correctness or maintainability:

- Entrypoint and Maven configuration for an executable JAR.
- Encapsulated domain model and immutable DNI.
- Dedicated text-file persistence responsibility and reconstruction at startup.
- One shared command dispatcher with separate sources of input (stdin/file).
- Explicit validation and rejection paths, preserving existing persistent state on failed operations.
- No premature design patterns, frameworks, databases, encryption, or later-delivery features.

Avoid turning recommendations into unrequested features. Where a design alternative is left open by the source, document the selected implementation and rationale rather than inventing a new externally visible requirement.
