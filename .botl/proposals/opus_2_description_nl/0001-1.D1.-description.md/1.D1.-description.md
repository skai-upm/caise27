# Amusement Park

## 1. Objective

The objective of this first delivery is to develop the foundation of a Java application for managing an amusement park. This delivery will implement only user management and the basic infrastructure needed to run the application. Features specific to the amusement park will be introduced gradually in subsequent deliveries. The application will be developed using Java 21, Maven, and Git. Development will proceed incrementally through the tasks described in this document. Each task must be reflected in the project Git history.

## 2. Phase 0 — Project creation

The first phase will take place in person during the first laboratory sessions. It will not be submitted, but it will provide the essential foundation for the project. It may be completed individually or in a group if one has already been formed. Its objective is to create and correctly configure the project used for the rest of the assignment, and to learn how to set up a project from scratch using Maven and upload it to Git (https://gitlab.etsisi.upm.es/).

### 2.1. Maven project

The project must be created using:

- JDK 21.
- Maven.
- The apache-maven-quickstart archetype.

Java projects created or submitted using a different structure will not be accepted in any subsequent course delivery.

### 2.2. Executable JAR

The project must generate an executable JAR file using Maven. It must be possible to build the project with:

```text
mvn package
```

The application must be executable from the terminal using:

```text
java -jar target/nombre-aplicacion.jar
```

In this case, the application must start in interactive mode and wait for commands from standard input. It must also accept a text file as an argument:

```text
java -jar target/nombre-aplicacion.jar input.txt
```

In this case, the application will process the commands contained in input.txt. Correct JAR generation and execution are mandatory requirements for every delivery.

## 3. Phase 1 — User management

### 3.1. User

Each user will have the following attributes:

- First name.
- Surname(s).
- DNI.
- Email address.
- Password.
- Telephone number.
- Card number.

The attributes must be properly encapsulated. A user’s DNI may not be changed after creation.

### 3.2. Separation of responsibilities

At a minimum, there must be separate classes to:

- represent a user;
- start and run the application;
- store and retrieve users.

The user class must not manage persistence directly. The main class must not directly contain the file-reading and file-writing logic either. The use of design patterns is not required in this delivery.

## 4. Command-based interface

All operations will be performed using text commands. The different elements of a command will be separated by the ; character. The application must interpret commands using basic String operations, including split. External libraries may not be used for this interpretation. Initially, the application must recognize the following commands:

```text
USER CREATE
USER DELETE
USER UPDATE
HELP
EXIT
```

An incorrect command must not cause the application to terminate unexpectedly.

## 5. User creation

The command format will be:

USER CREATE;FirstName;Surnames;DNI;Email;Password;Phone;Card

For example:

```text
USER CREATE;Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1
!;612345678;1234567890123456
```

User data must be validated before a user is stored.

### 5.1. DNI validation

The DNI must contain:

- eight digits;
- a final letter.

The application must verify that the letter correctly corresponds to the number according to the standard Spanish DNI validation algorithm. For example:

```text
12345678Z
```

is valid, whereas:

```text
12345678A
```

is not.

### 5.2. Email address validation

Basic email validation must be performed using String operations and split. Regular expressions may not be used. The expected format is:

text@text.xxx

There must be:

- content before @;
- content after @;
- a domain;
- an extension of exactly three characters.

Valid example:

```text
ana@correo.com
```

Invalid examples:

```text
ana
ana@correo
@correo.com
ana@.com
ana@correo.es
```

### 5.3. Password validation

The password must contain at least:

- one uppercase letter;
- one lowercase letter;
- one digit;
- one symbol.

Valid example:

```text
Clave1!
```

Invalid examples:

```text
clave1!
CLAVE1!
Clave!!
Clave12
```

Regular expressions and external libraries may not be used for this validation.

### 5.4. Card number validation

The card number must contain exactly 16 consecutive digits. Spaces, letters, and symbols are not allowed. Valid example:

```text
1234567890123456
```

Invalid examples:

```text
1234 5678 9012 3456
123456789012345
12345678901234567
```

### 5.5. Telephone number

In this first delivery, the telephone number only needs to be stored. Encryption or any other transformation is not required.

## 6. User uniqueness

Two users may not have the same:

- DNI;
- email address.

Both conditions must be checked before creating a user.

## 7. Persistence

Users must be preserved between different runs of the application. A text file will be used for this purpose. Each user will occupy one line, with attributes separated by the ; character. For example:

```text
Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1!;612345678;1234567890123456
Pedro;Lopez Martin;87654321X;pedro@correo.com;Otra2#;623456789;9876543210987654
```

Previously stored users must be loaded when the application starts. File reading and writing must be implemented in a class separate from the user class and the main class. The following may not be used:

- databases;
- persistence frameworks;
- external libraries for managing persistence.

## 8. User deletion

To delete a user, their email address and password must be provided. Format:

USER DELETE;Email;Password

Example:

```text
USER DELETE;ana@correo.com;Clave1!
```

The application must:

1. locate the user by email;

2. verify that the user exists;

3. check the password;

4. delete the user;

5. update persistent information.

An incorrect password must not allow the user to be deleted.

## 9. User modification

Format:

USER UPDATE;Email;Password;Field;NewValue

Examples:

```text
USER UPDATE;ana@correo.com;Clave1!;NAME;Ana Maria
USER UPDATE;ana@correo.com;Clave1!;EMAIL;ana.nueva@correo.com
USER UPDATE;ana@correo.com;Clave1!;PASSWORD;Nueva2#
USER UPDATE;ana@correo.com;Clave1!;CARD;9999888877776666
```

Modifiable fields must be represented by an enum. The following may be modified:

```text
NAME
SURNAME
EMAIL
PASSWORD
PHONE
CARD
```

The DNI may not be modified. Before any modification, the current email and password must be checked. The new values must satisfy the same validation rules established for user creation. In particular:

- a new email address must be valid and not used by another user;
- a new password must meet the established requirements;
- a new card number must contain exactly 16 digits.

Modifications must also update the persistent information.

## 10. Execution modes

### 10.1. Interactive mode

If the JAR is run without arguments:

```text
java -jar target/nombre-aplicacion.jar
```

the application must read commands from standard input. For example:

```text
USER CREATE;Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1
!;612345678;1234567890123456
USER UPDATE;ana@correo.com;Clave1!;PHONE;699999999
HELP
EXIT
```

After processing each command, the application will continue waiting for the next one.

### 10.2. File mode

The JAR must accept the path to a text file as its first argument:

```text
java -jar target/nombre-aplicacion.jar input.txt
```

The file will contain one command per line. For example:

```text
USER CREATE;Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1
!;612345678;1234567890123456
USER CREATE;Pedro;Lopez Martin;87654321X;pedro@correo.com;Otra2
#;623456789;9876543210987654
USER UPDATE;ana@correo.com;Clave1!;PHONE;699999999
EXIT
```

Commands must be processed in the order in which they appear. Blank lines will be ignored. Command processing must be identical whether commands come from interactive mode or from a file. A nonexistent or unreadable file must be handled in a controlled manner.

## 11. HELP command

The command:

```text
HELP
```

will display the available commands and their basic syntax. At a minimum, it must provide information about:

USER CREATE;<firstName>;<surnames>;<dni>;<email>;<password>;<phone>;<card> USER DELETE;<email>;<password> USER UPDATE;<email>;<password>;<field>;<value> HELP EXIT

## 12. EXIT command

The command:

```text
EXIT
```

will terminate the application in a controlled manner. In file mode, once EXIT is encountered, no subsequent lines may be processed. For example:

```text
USER CREATE;...
EXIT
USER CREATE;...
```

The second USER CREATE command must not be executed.

## 13. Technical restrictions

Delivery 1 must meet the following mandatory requirements:

- Java 21.
- Maven project.
- Standard Maven structure.
- Build using mvn package.
- Generation of an executable JAR.
- Interactive JAR execution.
- JAR execution with a .txt command file.
- Use of the Java standard library only.
- File-based persistence.
- Command processing using basic String operations and split.
- Separation of the user class, main class, and persistence class.
- Encapsulation of attributes.
- Project management using Git.

The following may not be used in this delivery:

- databases;
- frameworks;
- external libraries;
- regular expressions;
- encryption mechanisms.

## 14. Mandatory Git roadmap

The assignment must be developed incrementally. To verify this progression, a set of milestones is defined that must be reflected in the Git repository history. Each milestone must correspond to a functional and coherent state of the project. The commit messages listed below are mandatory and must be used exactly as written in this document. As many additional commits as necessary may be made before, after, or between mandatory milestones. Each milestone is not intended to consist solely of adding the items mentioned in its description. Students must determine which changes to existing code are necessary to correctly integrate each new feature.

### 14.1. F0-C01 — Project initialization

The first milestone corresponds to the project created during the initial laboratory session. At this point, the Maven project must have the correct structure, be configured to use JDK 21, and be compilable with Maven. The pom.xml file and the basic project structure must already be committed to the repository. The mandatory commit message is:

```text
[F0-C01] Initialize Maven project with JDK 21
```

### 14.2. F0-C02 — Executable application

By this point, the project must have evolved from a basic Maven project into an application that can be built and run independently of the development environment. Maven must produce a JAR file using mvn package that can be started using java -jar. The project must correctly define the class serving as the application entry point. The mandatory commit message is:

```text
[F0-C02] Configure executable JAR
```

### 14.3. F1-C01 — Adding the user to the domain

This milestone must introduce the concept of a user as defined in the assignment. Users must exist as independent objects within the system and retain the data needed for subsequent features. Their design must respect the basic encapsulation principles covered in the course and allow the management operations described in this delivery to be added later. The mandatory commit message is:

```text
[F1-C01] Add user model
```

### 14.4. F1-C02 — Valid users

From this milestone onward, the system must be able to determine whether data defining a user meets the restrictions specified in the assignment. Rules for DNI, email address, password, and card number must be considered. The solution must integrate with the existing model so that later user operations can reuse these checks when necessary. The mandatory commit message is:

```text
[F1-C02] Add user data validation
```

### 14.5. F1-C03 — User registration

At this milestone, the application must accept the USER CREATE command and use it to add new users to the system. The operation must satisfy all previously defined restrictions and preserve the uniqueness of DNI and email addresses. Students must decide how existing classes will cooperate to interpret the request, validate the data, and create the user. The mandatory commit message is:

```text
[F1-C03] Implement user creation
```

### 14.6. F1-C04 — User persistence

At this stage, users must no longer exist only during a single execution of the application. Information must be stored in the format specified in the assignment and loaded when the application starts again. This feature must respect the established separation of responsibilities, preventing the user model or main class from taking on responsibilities that do not belong to them. The mandatory commit message is:

```text
[F1-C04] Add user persistence
```

### 14.7. F1-C05 — User deletion

At this milestone, the application must add the ability to delete users using USER DELETE. The operation must be performed only when the identification conditions established in the assignment are met, and the result must also be reflected in persistent data. Operations from previous milestones must continue to work correctly. The mandatory commit message is:

```text
[F1-C05] Implement user deletion
```

### 14.8. F1-C06 — User modification

At this stage, the USER UPDATE command must be available. The application must allow changes to authorized fields using the enum defined to represent them, while keeping the DNI immutable. A modification must not introduce a state that would have been rejected during user creation; the relevant validation and uniqueness restrictions must therefore remain in force. Changes must persist between runs. The mandatory commit message is:

```text
[F1-C06] Implement user update
```

### 14.9. F1-C07 — Running command sequences

Until this point, the application may be used interactively. This milestone must also allow execution of a sequence of commands stored in a file whose path is provided as an argument when the application starts. The observable behavior of a command must be the same regardless of its source. Both input mechanisms must therefore be integrated with existing command processing, without maintaining two separate implementations of the operations. The mandatory commit message is:

```text
[F1-C07] Add command file input
```

### 14.10. F1-C08 — Execution control

At this milestone, the general HELP and EXIT commands must be added. The former will show the operations currently available in the application, while the latter will terminate it in a controlled manner. Their behavior must be consistent whether commands come from standard input or are processed from a file. In particular, a request to exit must prevent any subsequent command from being executed. The mandatory commit message is:

```text
[F1-C08] Add help and exit commands
```

### 14.11. F1-C09 — Delivery 1 integration

The final milestone represents the complete state of the first delivery. All developed features must work together, and the application must handle the different situations that may arise during use in a controlled manner, including input that cannot be processed correctly. The project must be buildable from scratch using Maven, and the resulting JAR must run independently of an IDE, both interactively and with an externally supplied command file. The mandatory commit message is:

```text
[F1-C09] Complete delivery 1 integration
```

## 17. Submission conditions

The submission must consist of the following elements:

1. The URL of the Git repository used to develop the assignment.

2. The executable JAR file generated by Maven.

### 17.1. Git repository

The repository must be accessible to the laboratory instructors throughout the evaluation process. The submitted URL must point to the repository actually used to develop the assignment. The repository must contain:

- the complete source code;
- the pom.xml file.
- the complete Maven project structure.
- the development Git history.
- all mandatory commits specified in the roadmap for this delivery.

A copy created only when the assignment is completed, or a repository lacking the actual development history, will not be accepted as a valid repository. If a private repository is used, students are responsible for ensuring that laboratory instructors have sufficient permissions to access the project and view its history.

### 17.2. Executable JAR

In addition to the Git repository, the executable JAR file generated by Maven must be submitted. The project must allow running:

```text
mvn package
```

and correctly produce the corresponding JAR. The instructors must be able to run the application directly using:

```text
java -jar target/nombre-aplicacion.jar
```

to use it in interactive mode. It must also support execution with a command file:

```text
java -jar target/nombre-aplicacion.jar input.txt
```

The input.txt file will be provided by the instructors during evaluation tests. The application must process this file without requiring an IDE, changes to the source code, or additional configuration.

### 17.3. Mandatory requirements

For the delivery to be evaluated, the following conditions must be met at a minimum:

- the Git repository is accessible to the laboratory instructors;
- the repository contains the complete development history;
- all mandatory commits from the roadmap are present;
- the project is a valid Maven project;
- the project compiles successfully using mvn package;
- an executable JAR is submitted;
- the JAR can run independently of the IDE;
- the JAR accepts a .txt file as command input.

The Git repository URL (https://gitlab.etsisi.upm.es/) and the executable JAR file jointly constitute the assignment submission.
