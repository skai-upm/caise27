## Why

Access restrictions should be modeled in the attraction type system, not merely as scattered runtime switches.

## What changes

- Add GENERAL, INDIVIDUAL, GROUP and SPECIAL attraction types.
- Use access-capability interfaces and meaningful bounded generics for ticket compatibility.
- Keep the old `ATTRACTION CREATE` syntax defaulting to GENERAL; support optional explicit type.

## Scope boundaries

- Do not create a separate individual-ticket hierarchy solely for SPECIAL.
- Pass consumption and additional entry checks belong to proposal 8.

## Proposed requirements for delta specs

- **R1:** The system SHALL support GENERAL, INDIVIDUAL, GROUP and SPECIAL attractions.
- **R2:** `ATTRACTION CREATE;<identifier>;<name>;<capacity>` SHALL create a GENERAL attraction; the four-parameter variant SHALL accept a type.
- **R3:** GENERAL attractions SHALL support individual and group tickets; INDIVIDUAL only individual; GROUP only group; SPECIAL only individual.
- **R4:** Ticket access capabilities SHALL be expressed using interfaces and bounded generics that constrain supported operations.
- **R5:** Previously stored attractions without an explicit type SHALL be interpreted as GENERAL.

## Key acceptance scenarios

### S1 — Backward compatible creation
- **Given** a valid three-argument attraction creation is received
- **When** the command executes
- **Then** a GENERAL attraction is created

### S2 — Explicit type
- **Given** a four-argument creation command specifies GROUP
- **When** the command executes
- **Then** the attraction is represented as GROUP

### S3 — Incompatible ticket
- **Given** a GROUP attraction receives an individual ticket
- **When** access is evaluated
- **Then** that ticket type is not accepted

### S4 — Special ticket model
- **Given** a SPECIAL attraction is configured
- **When** its ticket type is inspected
- **Then** it uses individual-ticket capabilities with additional attraction-specific conditions

````text
# F3-C07 — Generic attraction types

"Objective
Specialize attractions according to the accepted ticket type using interfaces and generics.
Description
The GENERAL, INDIVIDUAL, GROUP, and SPECIAL attraction types will be introduced.
The design must use interfaces to represent ticket access capabilities and bounded generic types to restrict which ticket classes different attractions may handle.
GENERAL attractions admit individual and group tickets; INDIVIDUAL admits only individual tickets; GROUP admits only group tickets; SPECIAL works with individual tickets, subsequently applying its additional Special Pass rules.
The E2 creation syntax remains valid and creates a GENERAL attraction. The new syntax allows the type to be specified explicitly.
Acceptance criteria
• 
All four attraction types exist.
• 
The E2 syntax without a type continues to work as GENERAL.
• 
The design uses at least one interface to represent access capabilities.
• 
Attractions use bounded generics functionally, not decoratively.
• 
GROUP does not admit an individual ticket.
• 
INDIVIDUAL does not admit a group ticket.
• 
SPECIAL uses an individual ticket as its basis for access.
Mandatory commit
[F3-C07] Add generic attraction access types"
````
