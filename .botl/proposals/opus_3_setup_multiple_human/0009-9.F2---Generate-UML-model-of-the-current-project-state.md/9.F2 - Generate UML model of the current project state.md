# F2 - Generate UML model of the current project state

DescriptionObjective: Document the object-oriented design currently present in the Amusement Park project using PlantUML.
Analyze the project's current implementation and generate a PlantUML class diagram that faithfully represents the existing code. The diagram must be derived from the actual implementation and must not change the design or introduce classes, interfaces, attributes, methods, or relationships that do not yet exist.
The diagram must include the relevant domain and current architecture classes and interfaces, showing, where applicable:
• 
classes and interfaces;
• 
inheritance and implementation relationships;
• 
associations and compositions;
• 
direction of relationships;
• 
multiplicities;
• 
relevant attributes;
• 
relevant public methods;
• 
enumerations used by the domain.
Particular attention must be paid to correctly representing relationships among users, groups, tickets, and attractions, including the currently implemented hierarchy for different ticket types.
Relationships must reflect their actual navigability in the code. Inverse relationships must not be added merely to make the diagram more complete.
The result must be saved in:
uml/model.puml
The generated file must be valid PlantUML and included in the project.
This task is exclusively for documenting the current state. No refactoring or functional code changes may be made to adapt the implementation to the diagram. If differences between the expected design and existing implementation are detected during analysis, the PlantUML must represent the existing implementation.
Acceptance criteria- The file uml/model.puml exists.

• 
The file can be processed correctly by PlantUML.
• 
The diagram represents the current state of the code.
• 
Relevant classes, interfaces, and enumerations are shown.
• 
Existing inheritance and implementation relationships are represented.
• 
Relevant associations and compositions are represented.
• 
Direction and multiplicities are indicated where they can be inferred from the code.
• 
The ticket hierarchy matches the current implementation.
• 
Relationships among users, groups, tickets, and attractions match the references actually present in the classes.
• 
No elements that have not yet been implemented are invented.
• 
Project behavior is not changed to perform this task.
• 
Do not represent usage relationships or methods in classes.
• 
Remove technical labels from attributes.
• 
Do not show an attribute if it is a relationship; objects should only have primitives and enumerations as attributes.
• 
If a class has no incoming relationships, its usage must be shown.
• 
Relationship names must match the name of the attribute in the containing class.
• 
Lines must have the cross marking the direction and which class holds the internal attribute.
