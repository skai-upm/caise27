I want to introduce a first functional epic for basic user management into the project.
The application will still run from the terminal, but all functional operations must be performed using text commands with an API-like format. Each received command must be interpreted by separating its components using Java's String.split.
This epic deals exclusively with users. Attractions, groups, tickets, fast passes, encryption, external libraries, and functionality from later phases must not yet be introduced.
Epic objective
The system must allow:
- creating users;
- deleting users;
- updating users;
- persistently storing users;
- retrieving stored users when the application starts again;
- validating entered data;
- preventing duplicate users by DNI or email address.
User model
Each user must store:
- First name
- Surname(s)
- DNI
- Email address
- Password
- Telephone number
- Card number
Attributes must be encapsulated.
The DNI is immutable after the user has been created.
Minimum separation of responsibilities
The solution must separate, at a minimum, the following responsibilities into independent classes:
- a class representing a user and storing its state;
- a main class responsible for starting the application and managing terminal interaction;
- an independent class responsible for storing users in the file and retrieving stored users.
The class representing a user must not directly read or write the file.
The main class must not directly implement the logic for storing data in or loading data from the file.
The class responsible for persistence must receive or return user objects as necessary, keeping user representation separate from user storage.
There is no need to introduce interfaces, design patterns, frameworks, or additional architectural layers that are not necessary to meet these requirements.
Command processing
The application will receive commands as text strings.
The command must be split using String.split to obtain the operation and its parameters.
External libraries must not be used to interpret commands.
The commands for this epic are:
USER CREATE
USER DELETE
USER UPDATE
The application must detect invalid commands or insufficient parameters and prevent them from unexpectedly terminating the program.
Creating a user
Format:
USER CREATE;Nombre;Apellidos;DNI;Correo;Contraseña;Telefono;Tarjeta
Example:
USER CREATE;Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1!;612345678;1234567890123456
The system must validate all data before creating the user.
If any required data is invalid, the user must not be stored.
DNI validation
It must be checked that the DNI is a valid Spanish national identity number.
It must contain:
- eight digits;
- one final letter.
The letter must match the eight digits according to the standard Spanish DNI validation algorithm.
Checking only the format is not sufficient.
Valid example:
12345678Z
Invalid example:
12345678A
Email validation
Basic validation must be performed using String operations and split.
Regular expressions must not be used.
The expected format is:
texto@texto.xxx
Validation must check at least:
- that a part exists before @;
- that a part exists after @;
- that the part after @ contains a period;
- that the domain is not empty;
- that the extension contains exactly three characters.
Valid example:
ana@correo.com
Invalid examples:
ana
ana@correo
@correo.com
ana@.com
ana@correo.es
Password validation
The password must contain at least:
- one uppercase letter;
- one lowercase letter;
- one digit;
- one symbol.
Validation must use standard Java functionality.
Regular expressions and external libraries must not be used.
Valid example:
Clave1!
Invalid examples:
clave1!
CLAVE1!
Clave!!
Clave12
Card number validation
The card number must contain exactly 16 consecutive digits.
The following are not allowed:
- spaces;
- letters;
- symbols;
- fewer or more than 16 characters.
Valid example:
1234567890123456
Invalid examples:
1234 5678 9012 3456
123456789012345
12345678901234567
Telephone number
In this epic, the telephone number must only be stored.
It must not yet be encrypted or processed using external libraries.
User uniqueness
Two users cannot have the same DNI.
Two users cannot have the same email address.
Both restrictions must be checked before creating a user.
For example, if the following already exists:
12345678Z;ana@correo.com
another user cannot be created with:
12345678Z;otro@correo.com
nor another with:
87654321X;ana@correo.com
Persistence
Users must be persistently stored in a text file.
Each user occupies one line.
Attributes are separated by the ; character.
Conceptual example of file contents:
Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1!;612345678;1234567890123456
Pedro;Lopez Martin;87654321X;pedro@correo.com;Otra2#;623456789;9876543210987654
Reading and writing this file must be implemented in a class independent of the User class and the application's main class.
No external persistence library may be used.
No database may be used.
Previously stored users must be recoverable when the application starts.
Deleting a user
To delete a user, the following must be provided:
- email address;
- password.
Format:
USER DELETE;Correo;Contraseña
Example:
USER DELETE;ana@correo.com;Clave1!
The operation must:
- find the user by email address;
- check that the user exists;
- check that the supplied password matches the stored password;
- delete the user;
- update the persistent file.
If the email address does not exist or the password is incorrect, the user must not be deleted.
Updating a user
To update a user, the following must be provided:
- current email address;
- current password;
- field to update;
- new value.
Format:
USER UPDATE;Correo;Contraseña;Campo;NuevoValor
Example of changing the first name:
USER UPDATE;ana@correo.com;Clave1!;NAME;Ana Maria
Example of changing the email address:
USER UPDATE;ana@correo.com;Clave1!;EMAIL;ana.nueva@correo.com
Example of changing the password:
USER UPDATE;ana.nueva@correo.com;Clave1!;PASSWORD;Nueva2#
Example of changing the card number:
USER UPDATE;ana.nueva@correo.com;Nueva2#;CARD;9999888877776666
Editable fields
Editable fields must be represented using an enum.
It must be possible to update:
- first name;
- surname(s);
- email address;
- password;
- telephone number;
- card number.
The DNI cannot be changed.
For example, the enum may conceptually represent values equivalent to:
NAME
SURNAME
EMAIL
PASSWORD
PHONE
CARD
The exact naming can be decided during design as long as it is consistent with the defined commands.
Validation during UPDATE
Before changing any data, the current email address and current password must be checked.
If an updated field has restrictions, its new value must be validated again.
In particular:
- a new email address must satisfy the specified format;
- a new email address must not belong to another user;
- a new password must meet all the specified requirements;
- a new card number must contain exactly 16 digits.
The DNI cannot be changed through USER UPDATE.
After a successful update, the persistent file must reflect the user's new state.
Technical constraints
The solution must:
- use Java 21;
- use Maven;
- continue from the project created using maven-archetype-quickstart;
- use only the Java standard library;
- receive operations through text commands;
- interpret commands using String.split;
- store users in a semicolon-separated text file;
- allow stored users to be reconstructed when the application starts;
- keep attributes encapsulated;
- keep the User representation, application main class, and storage/loading class separate;
- prevent User from directly knowing the persistence mechanism;
- prevent the main class from directly containing the implementation for reading and writing the file.
In this epic, the following must not be done:
- use regular expressions;
- use databases;
- use frameworks;
- use external libraries;
- use encryption;
- introduce attractions;
- introduce groups;
- introduce tickets;
- introduce fast passes;
- anticipate features from future phases;
- introduce design patterns solely with future requirements in mind.
The project must continue to compile and run its tests successfully using:
mvn test
Implementation must proceed incrementally, following the tasks generated for this epic, keeping the project functional after each significant increment.
