# Amusement Park — Delivery 3

## 1. Objective

The third delivery completes and reorganizes the system developed in previous phases, introducing new rules for park access and formalizing several object-oriented design mechanisms used throughout the assignment. From this delivery onward, the application must include different attraction types, personal passes associated with individual tickets, invoice generation using the Builder pattern, controllers with unique responsibility during execution, dependency injection, generics, exception handling, and protection of stored passwords. This phase focuses particularly on design patterns, interfaces, generics, exceptions, dependencies between objects, layered organization, and external dependencies managed through Maven. All features developed in Deliveries 1 and 2 must remain available and function correctly, except for extensions or modifications expressly stated in this document. The application will continue to use Java 21, Maven, and Git, generate an executable JAR, and support interactive execution, command-file execution, and temporary --fly mode.

## 2. Phase 3 — Advanced design and park extension

## 3. Layered application organization

The code must be reorganized so that presentation, business, and persistence responsibilities are clearly distinguishable. At a minimum, the project must have separate Java packages for:

- presentation, responsible for user interaction and command processing;
- business, responsible for the model, business rules, and application control elements;
- persistence, responsible for repositories and reading and writing persistent information.

These packages may be placed within the chosen root package and further divided into subpackages when necessary. The default package is not allowed. The reorganization must preserve the separation of responsibilities introduced in previous deliveries. In particular, the presentation layer must not access persistence files directly, and domain objects must not be responsible for directly storing or retrieving their persistent representations.

## 4. Handling exceptional situations

From this delivery onward, exceptions must be used to represent and propagate abnormal situations that may arise during system operations. Students may decide whether to use a centralized exception hierarchy or specific exceptions distributed across the different domain and application elements. In either case, exceptional situations must be handled in a controlled manner at the appropriate application level. An incorrect command or an operation that cannot be completed must not cause command processing to terminate unexpectedly. Exceptions must be used as part of the application design, not merely as a mechanical replacement for messages printed on screen.

## 5. Controllers and dependency injection

Classes responsible for controlling the main system entities and operations must ensure that only one instance of each exists when their responsibility represents a unique management function during an execution. These classes must explicitly apply the Singleton pattern when appropriate. This restriction must not be automatically extended to persistence components. Repositories must be regarded as replaceable dependencies. The design must assume that the same application may use different persistence implementations or configurations, and repositories therefore must not become global singletons simply because a controller uses them. Repository instances must be created and configured during application initialization and injected into the elements that require them. Likewise, when one controller needs to collaborate with another controller or service, that relationship should be established during initialization whenever necessary, rather than creating dependencies locally within each operation. For example, the design must allow normal persistence mode and --fly mode to use repositories configured with different paths without changing controller business logic.

Dependency injection must be implemented using Java code developed within the project. Dependency injection frameworks may not be used.

## 6. Invoice generation using Builder

The application must support invoice generation from the economic information available in the system. Invoices must be constructed by explicitly applying the Builder pattern. Each invoice must be built progressively from different parts or sections, including only those appropriate to the recipient type and available information. The design must provide a common abstraction for invoice construction. Whether to use one or multiple concrete builders for different invoice types is a student design decision, but the final object must be created through clearly differentiated steps, not through a single constructor with many optional parameters. Invoices will be generated on demand from the persisted system state. Generated invoice objects need not be persisted.

### 6.1. User invoice

An invoice for a user will be requested using:

INVOICE CREATE;USER;<email>

For example:

```text
INVOICE CREATE;USER;ana@correo.com
```

The user must exist as an active system user. The invoice must contain only the information applicable to that user. At a minimum, it must be able to include:

- the necessary identifying information of the user;
- individual tickets purchased directly for that user;
- SpeedPasses associated with their individual tickets;
- the Special Pass associated with their individual tickets, when present;
- the price of each included item;
- the total amount corresponding to the items shown.

Individual tickets belonging to a group ticket composition must not be counted again as an individual purchase on the user’s invoice, because their price is already included in the group ticket purchase. However, SpeedPasses and Special Passes associated with those individual tickets are personal purchases and must be able to appear on the corresponding user’s invoice. Sections with no information must be omitted rather than displayed as artificially empty sections.

### 6.2. Group invoice

An invoice for a group will be requested using:

INVOICE CREATE;GROUP;<groupIdentifier>

For example:

```text
INVOICE CREATE;GROUP;G01
```

The group must exist in the system. The invoice must contain only information applicable to the group. At a minimum, it must be able to include:

- the group identifier and name;
- group tickets purchased by the group;
- the composition of each group ticket when needed to describe the purchase;
- the total price of each group ticket;
- the total amount corresponding to the items shown.

Individual tickets forming part of a group ticket must not be added separately to the invoice total, because their price is already included in the group ticket price. Passes associated with members’ individual tickets are personal purchases and must not be automatically added to the group invoice total.

### 6.3. Conditional invoice construction

The Builder must allow an invoice to be constructed with only the elements relevant to the object being invoiced. User invoices and group invoices will share certain general elements, but meaningless fields must not be forced into them merely to obtain an identical structure. For example, a group invoice may need information on the composition of a group ticket, whereas a user invoice may need information on SpeedPasses or Special Passes. The solution must use the Builder pattern to avoid constructors with numerous optional parameters, null values used only to complete common signatures, or duplicated code that manually assembles each invoice variant. Students may choose the exact textual presentation of the invoice, provided it is legible, distinguishes the different items, and correctly shows their amounts.

## 7. Extended help

The HELP command will remain available and must continue to display the syntax of the commands recognized by the application. The following will also be added:

```text
HELP EXTENDED
```

This version must display a brief explanation of each command’s purpose alongside its syntax. The class responsible for generating help text must receive, through dependency injection, the behavior used to build that output. The design must be prepared to incorporate new ways of generating help in future extensions, without coupling these variants to the general logic for reading and executing commands.

## 8. Password protection

User passwords must no longer be stored in plain text. The application must add, via Maven, a basic library for applying BCrypt to passwords. For example, the jBCrypt dependency may be used:

```text
<dependency>
<groupId>org.mindrot</groupId>
<artifactId>jbcrypt</artifactId>
<version>0.4</version>
</dependency>
```

The password validation rules established in Delivery 1 must be applied before a new password is stored. The persistence file must not contain the original password; only its BCrypt-protected value may be stored. Operations that require password verification, such as USER DELETE or USER UPDATE, must validate the entered password against the stored value using the added library. When a password is changed, a new protected value must be generated and persisted. Automatic migration of user files generated by earlier versions of the assignment is not required.

## 9. Passes associated with individual tickets

The application will introduce two new elements associated with individual tickets:

- SpeedPass;
- Special Pass.

Both pass types are personal because they are associated with a specific individual ticket, not directly with a user. Passes may therefore also be associated with individual tickets that are part of a group ticket composition. Passes must have their own identity and retain, at a minimum, their identifier, price, associated individual ticket, and a Boolean indicator of whether they have been consumed.

A consumed pass must not disappear from the system. It must remain stored as a record of the purchase. The identifier space for passes must prevent duplicates among existing passes. This identifier space does not need to be shared with tickets.

### 9.1. Pass prices

A pass price will be calculated using the price stored in the individual ticket with which it is associated. The current price configured through SYSTEM PRICE will not retroactively change the price of a previously purchased ticket or, consequently, the price of passes later associated with it. Each SpeedPass will cost 20% of the associated individual ticket price. A Special Pass will cost the same as the associated individual ticket. If an individual ticket is part of a group ticket and already includes the relevant discount, its pass prices will be calculated using that discounted price.

### 9.2. SpeedPass

An individual ticket may have as many associated SpeedPasses as desired. SpeedPasses may be purchased individually or in packages of ten using:

SPEEDPASS CREATE;<purchaseIdentifier>;<individualTicket>;<quantity>

The quantity parameter may only take the values 1 or 10. For example:

```text
SPEEDPASS CREATE;SP01;T001;1
SPEEDPASS CREATE;SP02;T001;10
```

Each SpeedPass is an independent object. Identifiers for the created passes will be generated using:

<purchaseIdentifier>:<number>

For example, the second operation above will generate:

```text
SP02:1
SP02:2
SP02:3
...
SP02:10
```

Even a single-pass purchase will produce a pass identified according to the same rule, for example SP01:1. A purchase may be completed only if the individual ticket exists and its date is equal to or later than the current system date.

The application must check all required identifiers before completing a purchase. If any conflict exists, the operation must not partially create the package. Once the purchase is successfully completed, the total price charged must be displayed. Buying a package of ten does not apply any additional discount. Its total price is ten times the price of an individual SpeedPass.

### 9.3. Special Pass

An individual ticket may purchase at most one Special Pass throughout its entire existence. The purchase will be made using:

SPECIALPASS CREATE;<identifier>;<individualTicket>

For example:

```text
SPECIALPASS CREATE;PE01;T001
```

The individual ticket must exist and have a date equal to or later than the current system date. Once the purchase is successfully completed, the application must display the price charged. The Special Pass must have a state indicating whether it has been consumed. Once consumed, it must remain associated with the individual ticket as a historical record of the purchase. Consumption does not allow a second Special Pass to be purchased for the same ticket.

### 9.4. Pass refunds

Unconsumed passes may be refunded using:

SPEEDPASS DELETE;<speedPassIdentifier> SPECIALPASS DELETE;<specialPassIdentifier>

For SpeedPasses purchased in a package, each generated pass may be refunded separately using its specific identifier. A refund is allowed only if the pass has not been consumed and the date of its associated individual ticket is strictly later than the current system date. Passes associated with tickets valid for the current day or historical tickets may not be deleted independently. A consumed pass cannot be refunded. Deleting a pass represents refunding that purchase; the pass then ceases to be part of the system’s persisted state.

### 9.5. Deleting the associated ticket

The conditions established in Delivery 2 for deleting individual and group tickets remain in effect.

When a future individual ticket can validly be deleted through TICKET DELETE, all SpeedPasses and the Special Pass associated with that ticket must be deleted together. This must happen even if the passes were purchased in different operations. Similarly, when a future group ticket can validly be deleted through GROUPTICKET DELETE, the following must be removed:

1. all SpeedPasses and Special Passes associated with the individual tickets in its composition;

2. the individual tickets making up the composition;

3. the group ticket itself.

The operation must be consistent and must not leave partial deletions if it cannot be completed. Conceptually, this represents a joint refund of the ticket and its associated additional purchases.

## 10. Attraction types

From this delivery onward, attractions may place different restrictions on the type of ticket used for entry. The following types are defined:

```text
GENERAL;
INDIVIDUAL;
GROUP;
SPECIAL.
```

Creation may explicitly specify the type using:

ATTRACTION CREATE;<identifier>;<name>;<capacity>;<type>

For example:

```text
ATTRACTION CREATE;A01;Dragon Rojo;20;GENERAL
ATTRACTION CREATE;A02;Montana Rusa Individual;12;INDIVIDUAL
ATTRACTION CREATE;A03;Rafting Familiar;24;GROUP
ATTRACTION CREATE;A04;Pasaje del Terror;15;SPECIAL
```

For compatibility with Delivery 2, the earlier syntax:

ATTRACTION CREATE;<identifier>;<name>;<capacity>

will remain valid and will create an attraction of type GENERAL. Existing attractions in data compatible with this delivery that do not specify a type will be interpreted as general attractions.

### 10.1. General attractions

GENERAL attractions will accept individual and group tickets. Individual tickets may be used for normal entry or optionally with a SpeedPass. Group tickets may be used for normal entry or with SpeedPasses from all group members.

### 10.2. Individual attractions

INDIVIDUAL attractions will accept individual tickets only. Entry may take place normally or optionally with a SpeedPass. A group ticket may not be used directly to access this attraction type.

### 10.3. Group attractions

GROUP attractions will accept group tickets only. The group may enter normally or use SpeedPasses, in which case each individual ticket belonging to the composition must have an unconsumed SpeedPass.

### 10.4. Special attractions

SPECIAL attractions represent restricted-access activities in high demand, such as musical events, performances, or haunted-house experiences. They accept individual tickets only. Entry requires an unconsumed Special Pass associated with the individual ticket. Use of the Special Pass is automatic; the user must not specify an additional option in the entry command. Special attractions manage entry through their own queue and therefore do not accept SpeedPasses.

## 11. Interfaces and generics in attractions

The design of the different attraction types must use interfaces and generic types to represent and restrict permitted access types. Ticket access capabilities must be represented by suitable interfaces. Individual and group tickets must implement the appropriate capabilities, so that an attraction’s generic type restricts the kind of ticket it can handle. For example, general access, individual access, and group access capabilities may be distinguished conceptually. Attractions must use bounded generic types based on these interfaces. A generic parameter that has no actual effect on the operations permitted by an attraction will not be considered valid.

Both INDIVIDUAL and SPECIAL attractions operate with individual tickets. Their difference must not be artificially forced through a different ticket hierarchy: the additional Special Pass conditions form part of the special attraction’s own behavior.

## 12. Access to attractions

The syntax defined in Delivery 2 will be retained:

ATTRACTION ENTER;<attraction>;<ticket>

and an optional variant will be added:

ATTRACTION ENTER;<attraction>;<ticket>;SPEED

The operation must always check the conditions established in previous deliveries, including the existence of the attraction and ticket, validity for the current date, and available capacity. These checks will be supplemented with restrictions based on the attraction type and pass use.

### 12.1. Individual access with SpeedPass

When an individual ticket accesses an attraction that accepts SpeedPasses using:

```text
ATTRACTION ENTER;A01;T001;SPEED
```

at least one unconsumed SpeedPass must be associated with the ticket. If access completes successfully, exactly one available SpeedPass must be marked as consumed. If several SpeedPasses are available, the application may select any one but must indicate in its output which pass was consumed. If access fails for any reason, no SpeedPass may be modified.

### 12.2. Group access with SpeedPass

A group ticket may request access with SpeedPasses at GENERAL and GROUP attractions:

```text
ATTRACTION ENTER;A01;TG01;SPEED
```

In this case, each individual ticket in the composition must have at least one unconsumed SpeedPass. Before changing system state, the following must be checked at a minimum:

- the group ticket is valid for the current date;
- the attraction type accepts group tickets;
- there is sufficient capacity for all members;
- each individual ticket in the composition has an unconsumed SpeedPass.

Entry and pass consumption constitute an indivisible operation. If any condition fails, no member may enter and no SpeedPass may be consumed. If all conditions are satisfied, all members will enter and exactly one SpeedPass from each constituent individual ticket will be marked as consumed.

### 12.3. Access to special attractions

Access to a special attraction will use the normal syntax:

```text
ATTRACTION ENTER;A04;T001
```

The application must detect that the attraction is of type SPECIAL, automatically find the Special Pass for T001, and check that it has not been consumed. The Special Pass will be marked as consumed only when entry is successfully completed. The output must indicate that the Special Pass has been consumed. If the ticket has no Special Pass, the pass is already consumed, or any other access condition fails, the operation must be rejected without changing the state of the pass. The variant:

```text
ATTRACTION ENTER;A04;T001;SPEED
```

is not permitted at special attractions. A group ticket may not be used directly to enter a special attraction either.

## 13. Persistence

The persistence requirements established in previous deliveries remain in effect. Persistence must be extended to correctly preserve and reconstruct:

- the type of each attraction;
- SpeedPasses and the individual tickets to which they belong;
- Special Passes and the individual tickets to which they belong;
- the stored price of each pass;
- the consumed or unconsumed state of each pass.

Consumed passes must remain persisted while the corresponding ticket exists, as a record of the purchase. Valid ticket deletions must apply the cascading deletion rules established in this delivery.

The --fly mode must include the new persistent elements using the same repositories and persistence mechanisms as normal mode, changing only their configuration. The collection of users inside attractions remains temporary execution state and must not be persisted. Automatic Java object serialization and databases are not permitted. The general restriction from previous deliveries on external libraries remains in effect, except for the BCrypt dependency used to protect passwords and other dependencies expressly authorized by the instructors.

## 14. UML representation

The file:

```text
uml/model.puml
```

must be updated to represent the final design of Delivery 3. In addition to the elements required in Delivery 2, the model must make it possible to identify:

- the new access interfaces used by tickets;
- the use of generics in attractions;
- the different attraction types;
- relationships between individual tickets and passes;
- the cardinality corresponding to Special Passes and SpeedPasses;
- classes or abstractions used by the Builder pattern for invoice generation;
- relevant relationships resulting from dependency injection;
- elements needed to represent construction of user and group invoices;
- controllers whose uniqueness is part of the design.

It is not necessary to represent every implementation detail or every defined exception, but the diagram must be consistent with the code actually submitted.

ATTRACTION CREATE;<identifier>;<name>;<capacity>;<type> ATTRACTION ENTER;<attraction>;<ticket> ATTRACTION ENTER;<attraction>;<ticket>;SPEED SPEEDPASS CREATE;<purchaseIdentifier>;<individualTicket>;<quantity> SPEEDPASS DELETE;<speedPassIdentifier>

SPECIALPASS CREATE;<identifier>;<individualTicket> SPECIALPASS DELETE;<specialPassIdentifier> INVOICE CREATE;USER;<email> INVOICE CREATE;GROUP;<groupIdentifier> HELP HELP EXTENDED EXIT

The syntax of commands from Deliveries 1 and 2 must continue to appear and work. HELP EXTENDED must also include a clear description of each command’s purpose.

## 16. Technical restrictions

Delivery 3 must retain all compatible technical requirements established in previous phases. The project must continue to use Java 21 and Maven and generate, using:

```text
mvn package
```

an executable JAR. The application must use a layered organization reflected in Java packages. Invoice generation must be implemented using the Builder pattern. Control classes that represent unique management responsibilities must apply Singleton. Repositories must not become Singletons by default and must be replaceable or configurable during application initialization. Dependencies among repositories, controllers, and services must be provided by dependency injection where appropriate. Password protection must use BCrypt included as a Maven dependency. Attractions must use bounded generics and interfaces to restrict which access types they can handle. Consumed SpeedPasses and Special Passes must not be deleted as a consequence of use. Group operations involving entry and consumption of multiple SpeedPasses must be atomic. Features from Deliveries 1 and 2 may not be removed or replaced with incompatible alternatives, except for modifications expressly indicated in this delivery.

## 19. Basic execution example

The following example illustrates one possible valid sequence using some features introduced in this delivery. It is not intended to cover every situation that the application must handle.

```text
SYSTEM DATE;2027-04-15
SYSTEM PRICE;40.00
USER CREATE;Ana;Garcia Lopez;12345678Z;ana@correo.com;Clave1
!;612345678;1234567890123456
USER CREATE;Pedro;Lopez Martin;87654321X;pedro@correo.com;Otra2
#;623456789;9876543210987654
USER CREATE;Laura;Martin Ruiz;11111111H;laura@correo.com;Laura3$
;634567890;1111222233334444
GROUP CREATE;G01;Familia Garcia
GROUP ADD;G01;ana@correo.com
GROUP ADD;G01;pedro@correo.com
GROUP ADD;G01;laura@correo.com
ATTRACTION CREATE;A01;Dragon Rojo;20;GENERAL
ATTRACTION CREATE;A02;Montana Individual;12;INDIVIDUAL
ATTRACTION CREATE;A03;Rafting Familiar;12;GROUP
ATTRACTION CREATE;A04;Pasaje del Terror;15;SPECIAL
TICKET CREATE;T001;ana@correo.com;2027-04-15
GROUPTICKET CREATE;TG01;G01;2027-04-15
SPEEDPASS CREATE;SP01;T001;10
SPECIALPASS CREATE;PE01;T001
SPEEDPASS CREATE;SP02;TG01:12345678Z;1
SPEEDPASS CREATE;SP03;TG01:87654321X;1
SPEEDPASS CREATE;SP04;TG01:11111111H;1
ATTRACTION ENTER;A01;T001
ATTRACTION EXIT;A01;ana@correo.com
ATTRACTION ENTER;A02;T001;SPEED
ATTRACTION EXIT;A02;ana@correo.com
ATTRACTION ENTER;A03;TG01;SPEED
ATTRACTION EXIT;A03;ana@correo.com
ATTRACTION EXIT;A03;pedro@correo.com
ATTRACTION EXIT;A03;laura@correo.com
ATTRACTION ENTER;A04;T001
ATTRACTION EXIT;A04;ana@correo.com
INVOICE CREATE;USER;ana@correo.com
INVOICE CREATE;GROUP;G01
```

```text
HELP
HELP EXTENDED
EXIT
```

When SP01 is purchased, each SpeedPass will cost 20% of the price stored in T001, and the application will display the total price of the ten passes. Creating PE01 will show a price equal to that of T001. Entry to A02 using SPEED will consume exactly one of Ana’s SpeedPasses. Entry of TG01 to A03 with SPEED will first check that all three members have an unconsumed pass and, if entry succeeds, will consume exactly one from each member. Entry to A04 will automatically locate and consume Ana’s Special Pass and report this operation. INVOICE CREATE operations will generate invoices using the corresponding Builder. Ana’s invoice will include only her applicable personal purchases, whereas G01’s invoice will include the group tickets purchased by the group without individually counting their constituent tickets again.

The submission must consist of the URL of the same Git repository used in previous phases and the new executable JAR generated for this delivery. The repository must preserve the complete history from Phase 0 through Phase 3. In addition to the source code, Maven project, and previously required elements, it must contain the updated PlantUML file. The instructors must be able to build the project using:

```text
mvn package
```

and execute the resulting JAR with an external command file:

