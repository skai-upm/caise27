## Why

Delivery 3 must be reliable end-to-end while preserving the behavior built in Deliveries 1 and 2.

## What changes

- Run complete regression tests across all existing and F3 commands and execution modes.
- Confirm executable JAR, normal and temporary persistence, both HELP variants, and UML accuracy.
- Fix only integration defects discovered in verification.

## Scope boundaries

- Do not introduce new product functionality outside the completed deliveries.
- Do not rewrite passing code without a demonstrated integration defect.

## Proposed requirements for delta specs

- **R1:** The application SHALL package into an executable JAR using `mvn package`.
- **R2:** All E1, E2 and F3 commands SHALL remain usable through shared command processing.
- **R3:** Interactive, file and `--fly` execution SHALL work with the final repository/controller configuration.
- **R4:** Both `HELP` and `HELP EXTENDED` SHALL include applicable new commands.
- **R5:** Normal and temporary persistence SHALL correctly handle final F3 state.
- **R6:** `uml/model.puml` SHALL correspond to the final implementation.

## Key acceptance scenarios

### S1 — End-to-end command sequence
- **Given** representative E1, E2 and F3 commands are supplied in one valid input file
- **When** the JAR processes the file
- **Then** the commands work together without losing previous functionality

### S2 — Temporary run
- **Given** the application is launched with --fly and a command file
- **When** the run exits
- **Then** normal persistent state remains unchanged

### S3 — Help coverage
- **Given** all final commands are available
- **When** HELP and HELP EXTENDED execute
- **Then** the former shows syntax and the latter adds command descriptions

### S4 — Release verification
- **Given** the current project tree is built
- **When** `mvn package` and the regression suite run
- **Then** the executable JAR is built and tests pass
