# Change 3 — Interactive and file-based command execution

**Suggested change ID:** `add-command-execution-modes-and-control`

## Why

Make the existing user commands executable both manually and in a repeatable batch file, and add general help and controlled shutdown without duplicating business logic.

## What changes

- When launched without arguments, read one text command per line from standard input until `EXIT` or end-of-input.
- When the first `main` argument is a path, read the file sequentially, ignore blank lines and process its nonempty lines through the **same** command execution path used by interactive mode.
- Add `HELP` to show the user commands and their basic syntax, and `EXIT` to stop processing promptly in either mode.
- Report missing, inaccessible or unreadable command files in a controlled way, without exposing an unhandled exception.
- Preserve all existing user management, persistence, validation, and JDK 21/Maven behavior.

## Scope and constraints

**In scope:** input source selection, sequential command reading, shared command dispatch, HELP/EXIT behavior, handling invalid files and blank lines, regression tests.

**Out of scope:** new user attributes, modified user-validation rules, attractions, tickets, groups, passes, GUI, external command libraries, frameworks, speculative future features or unnecessary patterns.

**Capabilities:** new `command-input-modes` and `application-control`; modify existing `user-management` command dispatch **only as needed** to share its processing across input sources.

## Requirements and acceptance scenario map

### Input modes

- **Interactive:** The application SHALL read each standard-input line as a command when no file argument is passed; after executing a non-EXIT command, it SHALL await the next one, stopping on EXIT or EOF.
- **File:** The application SHALL interpret its first argument as a file path, read the file line by line in original order, skip blank lines, and run commands using the same parser and execution behavior as interactive mode.
- **Shared processing:** Each identical sequence of valid commands SHALL have the same observable results from a file or from standard input.

**Scenario — Interactive session:** Given the application starts without arguments, when a user issues `USER CREATE`, then `USER UPDATE`, then `HELP`, then `EXIT`, then all commands before EXIT are processed and the application terminates after EXIT.

**Scenario — Equivalent file run:** Given a text file containing the same command sequence, when it is passed as the first launch argument, then commands have equivalent effects and process in the supplied order.

**Scenario — Blank lines:** Given a file with empty lines between valid commands, when processed, then empty lines are skipped and valid commands still execute.

### Help and exit

- **HELP:** The system SHALL expose `HELP` and display at least the basic syntax for `USER CREATE`, `USER DELETE`, `USER UPDATE`, `HELP`, and `EXIT`. The help behavior SHOULD remain straightforward to update as later deliveries add commands; do not implement those commands now.
- **EXIT:** The system SHALL stop accepting/processing subsequent commands after `EXIT`, regardless of the input source.

**Scenario — Help content:** Given Delivery 1 command support, when `HELP` is executed, then all five listed commands and their usage syntax are displayed.

**Scenario — No commands after EXIT:** Given a file contains valid create, then `EXIT`, then another create, when executed, then the first create runs and the second does not run.

### Error containment and compatibility

- **File errors:** The system SHALL handle a missing, non-openable, or unreadable file without uncaught Java exceptions and shall stop in a controlled manner.
- **Compatibility:** User creation, modification, deletion, validation and persistence SHALL remain unchanged and working through either input source.

**Scenario — Missing file:** Given a nonexistent file path, when the application starts in file mode, then it reports the problem and exits without uncaught exception output.

**Scenario — Regression:** Given user-management commands known to work before this change, when run interactively or through the file, then their results and persisted effects remain equivalent.

## Design and task guidance

Document the startup dispatch between standard input and file input, the single shared command parser/processor, and how EXIT stops both loops. Plan tasks to add mode selection, input reading, HELP, EXIT, controlled file errors, and tests for equivalence, EOF, blank lines, invalid files, and regression. Keep `mvn test` passing. Do not rewrite the user domain model merely to add input modes.

Objective
Extend the application to support command execution both interactively from the terminal and from an input file, and add general commands to display available operations and properly terminate the application.
This extension must fully preserve previously developed user-management functionality.
1. Interactive mode
The application must be executable without arguments.
In this mode, it must continuously read commands from standard input.

USER UPDATE;ana@correo.com;Clave1!;PHONE;699999999
HELP
EXIT

After processing a command, the application must continue waiting for new commands until it receives EXIT or standard input ends.

The application must allow a path to a text file containing commands to be supplied as its first execution argument.
For example:input_basico.txt

- execute commands in the order in which they appear;
- use exactly the same command processing as interactive mode.
There must not be separate implementations of commands for file and interactive modes.

8. Shared processing
Interactive mode and file mode are merely two different ways to provide commands to the application.
Command interpretation and execution must be shared.
The logic for the following must not be duplicated:
- USER CREATE;
- USER DELETE;
- USER UPDATE;
- HELP;
- EXIT.
The same command must yield the same result whether supplied via terminal or file.

Acceptance criteria
