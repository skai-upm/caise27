Objective: Introduce a single simulated date for the entire application, allowing time-dependent operations to be executed and tested without directly using the computer's real date.
Description:
The application must have a configurable current system date set through commands. All functionality requiring date checks must use this date.
The command will be added:SYSTEM DATE;yyyy-MM-dd
Example:SYSTEM DATE;2026-09-15
The date must be stored in the application's main controller and be unique throughout the system. All time-dependent operations must use this date instead of directly consulting the computer's real date.
The implementation must allow the date to be freely changed backward or forward to facilitate testing.
This delivery does not specify or require use of the Singleton pattern.
Main acceptance criteria:
• 
 The command can set a valid date. 
• 
 A date in an incorrect format is rejected. 
• 
 There is one current date for the entire application. 
• 
 Changing the date immediately affects subsequent operations. 
• 
 No time-dependent business rule directly uses the computer's real date.
• 
Executions start with the operating system's current date, so this system variable need not be persisted.

Objective: Introduce the park's attractions and integrate users, groups, and tickets through individual and group access, while also allowing the current status of each attraction to be queried.
Description:
The application must allow attractions to be created and managed.
Each attraction will have at least:
• 
identifier;
• 
name;
• 
maximum capacity;
• 
collection of users currently present.
Example:ATTRACTION CREATE;A01;Tornado;20
Visitors will enter attractions using their tickets.
Access must be possible using either an individual ticket or a group ticket:ATTRACTION ENTER;A01;T001
ATTRACTION ENTER;A01;TG01
When an individual ticket is used, the corresponding user is added to the attraction.
When a group ticket is used, the users corresponding to the individual tickets composing that group ticket are added.
The attraction must handle both access types uniformly using object-oriented mechanisms, avoiding unnecessary duplication of access logic for each ticket type.
The ticket used must be valid for the current date configured through SYSTEM DATE.
Entry must also not exceed the attraction's maximum capacity. If an entire group attempts to enter and there is insufficient capacity for all its members, none may enter.
For example, if three places remain and a group ticket represents four users:ATTRACTION ENTER;A01;TG01
the entire operation must be rejected.
Operations must also be provided for leaving an attraction and freeing the capacity occupied by those users.
In addition, the application must allow the current status of an attraction to be queried through:ATTRACTION STATUS;A01
ATTRACTION STATUS must display at least:
• 
 attraction identifier; 
• 
 name; 
• 
 maximum capacity; 
• 
 number of users currently present; 
• 
 number of available places; 
• 
 users currently present in the attraction. 
The information must represent the attraction's actual state at the time of the command, whether users entered on individual tickets or as members of a group ticket.
For example, after running:ATTRACTION ENTER;A01;T001
ATTRACTION ENTER;A01;TG01
ATTRACTION STATUS;A01
the query must reflect both the user associated with T001 and the users associated with the individual tickets contained in TG01.
After an exit operation:ATTRACTION EXIT;A01;T001
ATTRACTION STATUS;A01
the displayed status must immediately reflect the released capacity.
The student may decide the exact format of ATTRACTION STATUS output provided it is understandable and contains all required minimum information.
Main acceptance criteria:

 The command ATTRACTION STATUS;IdentificadorAtraccion exists.

A temporary execution mode is required that allows all of the application's
persistence facilities to be used without modifying the persistent data from a
normal execution.
When the application is run with the parameter:
--fly
it must create, at startup, an independent temporary directory that
will be used as the location of all the system's persistence files.
The directory must be identified by a timestamp that distinguishes
each execution. For example:
tmp/20260826_190315/
During that execution, all repositories must use exclusively
the files contained in that temporary directory. This includes
persistence for users, groups, tickets, group tickets, attractions, and
any other persistent element in the project.
Repository functionality must not be duplicated or implemented
specifically for --fly mode. The difference between normal
and temporary execution must be handled by configuring the
paths used for persistence.
When the application terminates, the temporary directory created for that run
must be deleted together with all the files it contains.
Deletion must also occur when execution ends via
the EXIT command.
--fly mode must be compatible both with interactive execution and with
execution using a command file.
Examples:
java -jar target/parque.jar --fly
java -jar target/parque.jar --fly input_fase2.txt
When --fly is not used, the application must preserve exactly the
existing permanent-persistence behavior.
The purpose of this mode is to allow isolated runs and tests
without altering the application's persistent state.
