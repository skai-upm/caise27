## Why

The current application mixes concerns accumulated during Deliveries 1 and 2. Separate presentation, business, and persistence without altering observable behavior.

## What changes

- Move command interaction and parsing into `presentation`, domain rules and controllers into `business`, and repositories/file I/O into `persistence`.
- Remove any classes from the Java default package.
- Keep existing command contracts, persistence data, and E1/E2 behavior unchanged.

## Scope boundaries

- No new functional commands, data formats, or business rules.
- This is a structural refactor, not a reason to introduce later F3 functionality.

## Proposed requirements for delta specs

- **R1:** The application SHALL use distinct Java packages for presentation, business, and persistence responsibilities.
- **R2:** Presentation code SHALL NOT directly read or write persistence files.
- **R3:** Domain model objects SHALL NOT implement file storage or loading.
- **R4:** All E1 and E2 commands SHALL retain their existing inputs and outcomes after reorganization.

## Key acceptance scenarios

### S1 — Legacy command behavior
- **Given** a valid E1/E2 command sequence and existing persisted data
- **When** the same sequence is run after the refactor
- **Then** the observable results and persisted records remain equivalent

### S2 — Package boundaries
- **Given** the reorganized source tree
- **When** the Java packages and dependencies are inspected
- **Then** presentation, business, and persistence are separated and no class uses the default package

### S3 — Build
- **Given** the refactor is complete
- **When** `mvn package` runs
- **Then** the executable JAR is generated successfully

# F3-C01 — Reorganize application into layers

"Objective
Reorganize the existing code to physically separate presentation, business, and persistence responsibilities into distinct Java packages, preserving all features from previous deliveries.
Description
The application must be structured into at least the presentation, business, and persistence layers, with additional subpackages where necessary. The presentation layer handles command-based interaction; the business layer contains the model, domain rules, and controllers; the persistence layer contains repositories and file access.
The reorganization must not change the syntax or behavior of existing commands.
Acceptance criteria
• 
Separate packages exist for presentation, business, and persistence.
• 
The default package is not used.
• 
Commands do not directly access persistence files.
• 
Domain objects do not directly handle file reading or writing.
• 
All E1 and E2 commands continue to work.
• 
The project still builds with mvn package.
Mandatory commit
[F3-C01] Reorganize application into layered packages"
