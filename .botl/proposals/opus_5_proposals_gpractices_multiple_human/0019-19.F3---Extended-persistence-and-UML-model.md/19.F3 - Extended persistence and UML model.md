## Why

New passes and attraction types must survive restarts, and valid ticket deletion must clean up owned records consistently.

## What changes

- Extend file persistence for pass identity, associated ticket, price, consumption and attraction type.
- Cascade delete passes with eligible individual or group ticket deletion, preserving atomicity.
- Update `uml/model.puml` to reflect implemented F3 classes and relations.

## Scope boundaries

- Preserve existing normal and `--fly` modes.
- UML describes code as implemented; do not add speculative elements.

## Proposed requirements for delta specs

- **R1:** Persistent storage SHALL reconstruct pass identity, stored price, associated ticket and consumed status after restart.
- **R2:** Persistent storage SHALL preserve attraction type and treat compatible prior entries without an explicit type as GENERAL.
- **R3:** Valid `TICKET DELETE` SHALL also remove associated passes; valid `GROUPTICKET DELETE` SHALL remove the group-ticket constituents and their passes consistently.
- **R4:** If any deletion fails, the system SHALL NOT leave a partial cascade deletion.
- **R5:** `--fly` SHALL isolate all newly persisted F3 elements as well as pre-existing data.
- **R6:** `uml/model.puml` SHALL be valid PlantUML and reflect the implemented F3 model and relevant relationships.

## Key acceptance scenarios

### S1 — Restart
- **Given** a purchased pass has been consumed
- **When** the application restarts normally
- **Then** pass identity, price, ticket link and consumed status are retained

### S2 — Individual cascade
- **Given** a future individual ticket has associated passes
- **When** valid TICKET DELETE executes
- **Then** the ticket and its passes are removed together

### S3 — Group cascade
- **Given** a future group ticket contains individual tickets with passes
- **When** valid GROUPTICKET DELETE executes
- **Then** passes, constituents and group ticket are removed consistently

### S4 — Failure safety
- **Given** a deletion fails validation or during processing
- **When** the operation ends
- **Then** no partial deletion remains

### S5 — Temporary isolation
- **Given** an execution uses --fly
- **When** F3 data is written and the execution ends
- **Then** normal persistent data is untouched and temporary storage cleanup follows existing rules

# F3-C09 — Extended persistence and UML model

"Objective
Persist the new E3 state and update the PlantUML model.
Description
Persistence must reconstruct passes, their prices, their associated individual tickets, and consumed status. It must also retain the type of each attraction.
When a future individual ticket is validly deleted, all associated SpeedPasses and its Special Pass must be cascade-deleted. When a future group ticket is validly deleted, passes associated with each individual ticket in its composition must be deleted first, then those individual tickets, and finally the group ticket.
The uml/model.puml file must be updated to represent the new classes, interfaces, generics, associations, and relevant relationships.
Acceptance criteria
• 
Passes are correctly reconstructed between executions.
• 
The consumed status is preserved.
• 
Each pass's price is preserved.
• 
The attraction type is preserved.
• 
TICKET DELETE cascade-deletes associated passes.
• 
GROUPTICKET DELETE consistently removes passes, constituent tickets, and the group ticket.
• 
A failed deletion leaves no partial deletions.
• 
--fly also applies to the new data.
• 
uml/model.puml reflects the actual E3 design.
Mandatory commit
[F3-C09] Extend delivery 3 persistence and UML"
