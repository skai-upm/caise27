## Why

Controllers need controlled application-wide lifetimes, while repository implementations and storage paths must remain replaceable.

## What changes

- Apply explicit Singleton behavior to controller responsibilities that must be unique per execution.
- Construct/configure repositories at application startup and inject them into consuming components.
- Wire controller-to-controller/service dependencies during initialization rather than locally in business operations.

## Scope boundaries

- Repositories are not required to be Singletons and must remain replaceable.
- No external dependency-injection framework.
- Preserve the normal and `--fly` persistence behavior.

## Proposed requirements for delta specs

- **R1:** Each controller responsible for a unique application management function SHALL explicitly enforce one instance per execution.
- **R2:** Repositories SHALL be replaceable and SHALL NOT be made global Singletons merely because controllers use them.
- **R3:** Repository instances SHALL be initialized and provided to consumers through dependency injection.
- **R4:** Controller collaborations SHALL be wired during application startup where required.
- **R5:** The same controller business logic SHALL work with normal and `--fly` repository paths.

## Key acceptance scenarios

### S1 — Unique controllers
- **Given** a controller has a unique management responsibility
- **When** different application elements request access to it
- **Then** they access the same controller instance within one execution

### S2 — Repository substitution
- **Given** the application starts once normally and once with `--fly`
- **When** repositories are configured
- **Then** the paths differ without altering the controller business logic

### S3 — No local construction
- **Given** a business operation needs persistence or another service
- **When** the operation runs
- **Then** it uses its injected dependency rather than constructing a repository inside the operation

# F3-C03 — Singleton and dependency injection

"Objective
Formalize the uniqueness of controller classes and configure collaboration among components through dependency injection.
Description
Controller classes representing a single management responsibility within the application must guarantee a single instance through the Singleton pattern.
Persistence repositories must not be considered single instances. The design must assume that an application may use different repository implementations or configurations. Necessary instances must be created/configured at startup and injected into the components that use them.
When a controller needs to collaborate with another controller or service, the dependency must be configured during application initialization rather than constructed locally inside the operation using it.
Acceptance criteria
• 
Controllers that are conceptually unique apply Singleton.
• 
Repositories are not required to be implemented as Singletons.
• 
Repositories are created/configured at startup and injected.
• 
Normal and --fly modes can use repositories with different paths without changing controller logic.
• 
Required dependencies among controllers are established during initialization.
Mandatory commit
[F3-C03] Add singleton controllers and dependency injection"
