# F2 — Amusement Park: Integrated OpenSpec Change

> **OpenSpec change prompt.** Develop **one comprehensive change** extending the existing F1 Amusement Park application with all seven functional areas below. The full, unedited input is retained in **Appendix A** as the authoritative reference. Do not interpret this as seven independently archived changes.

## Why

F1 supports project setup, user management, persistence, and text-command execution. F2 introduces date-dependent park operations, user groups, ticket purchases, discounts, attractions, UML documentation, and temporary persistence. These features must work together while preserving existing F1 behavior. The specification must make invariants and testable outcomes explicit before implementation.

## What changes

1. Introduce a single configurable system date shared by all date-dependent operations.
2. Manage groups of existing users and persist group membership.
3. Create and delete dated individual tickets, manage a runtime base ticket price, and enforce ticket-dependent user deletion restrictions.
4. Support group-ticket composition, price discounts, deletion, and group membership locking.
5. Create attractions and support atomic group admission, individual admission, departures, and status queries.
6. Generate a PlantUML diagram **from the actual implemented code**.
7. Add isolated `--fly` execution with configurable repository paths and clean-up on termination.

## Scope and compatibility

**In scope:** the seven areas above, their interactions, file-backed persistence, tests, existing terminal/file command handling, and necessary updates to command help. Preserve existing F1 functionality and Java/Maven constraints.

**Out of scope:** implementation of the F3 SpeedPass, Special Pass, invoice Builder, BCrypt, advanced attraction categories, and Singleton adoption as a new requirement. Do not introduce functionality merely because it may be needed by later deliveries. Do not create a new web/API interface or database.

**Backward compatibility:** Existing F1 commands and both input modes SHALL continue to work. Use the shared command parser/executor. Preserve historical records and existing persisted data to the extent required by the provided specifications. Do not silently change a previously defined command's syntax.

## Normative requirements and acceptance scenarios

### 1. System date

**DATE-01** The application SHALL initialize a single runtime system date to the operating system's current local date at startup. This runtime setting SHALL NOT need persistence.

**DATE-02** `SYSTEM DATE;yyyy-MM-dd` SHALL set the date if valid, SHALL reject malformed dates without altering the previous value, and SHALL permit advancing or moving backward.

**DATE-03** All park business checks relying on the current date SHALL use this centralized setting rather than repeatedly querying the operating system date. This requirement does not prescribe the Singleton pattern.

#### Scenario: Date updated for subsequent operations
- **GIVEN** a running application with a configured date
- **WHEN** `SYSTEM DATE;2026-09-15` is executed
- **THEN** subsequent date-sensitive commands evaluate against September 15, 2026.

#### Scenario: Invalid date
- **GIVEN** a configured date
- **WHEN** an invalid `SYSTEM DATE` value is submitted
- **THEN** the request is rejected and the configured date remains unchanged.

### 2. Group management

**GROUP-01** Groups SHALL have an identifier, name, and collection of references to **existing** users; they SHALL NOT create duplicate user objects.

**GROUP-02** The application SHALL provide `GROUP CREATE`, `GROUP ADD`, `GROUP REMOVE`, and `GROUP DELETE` with the command syntax and examples in Appendix A.

**GROUP-03** Group membership SHALL reject unknown users and duplicate membership. Changes to groups SHALL be persisted, with membership correctly reconstituted after restart.

**GROUP-04** Once group-ticket locks are introduced, operations that alter/delete a locked group SHALL be rejected as required in Section 4 below.

#### Scenario: Restore membership
- **GIVEN** existing users have been added to a group
- **WHEN** the application restarts in normal persistence mode
- **THEN** the group contains references to the correctly restored users, with no duplicated users.

#### Scenario: Invalid membership
- **GIVEN** a group exists
- **WHEN** an unknown user or an already-present user is added
- **THEN** the operation fails without changing group membership.

### 3. Individual tickets and base price

**TICKET-01** Each individual ticket SHALL retain a unique identifier, use date, associated user reference, and purchase price. It SHALL be created only for an existing user on an allowable date, taking the configured system date into account.

**TICKET-02** `TICKET CREATE;T001;ana@correo.com;2026-10-15` SHALL create a ticket when valid and return the defined success text `OK TICKET CREATED -> <Precio>` with the purchase price. Preserve the exact text pattern from the input.

**TICKET-03** The runtime base price SHALL initialize to `40.00` on each run and SHALL be changeable via `SYSTEM PRICE;60.00`. The **runtime base-price setting** need not persist; the **price already recorded on a purchased ticket** SHALL persist as part of that ticket. Changing the base price SHALL NOT retroactively modify purchased tickets.

**TICKET-04** Individual tickets SHALL persist across runs. Past tickets SHALL be retained as historical records.

**TICKET-05** `TICKET DELETE;<ticketId>` SHALL be permitted only if the ticket date is *strictly later* than the system date, and SHALL be rejected for today and past dates.

**TICKET-06** `USER DELETE` SHALL be rejected if an associated ticket is dated today or in the future. A historical ticket alone SHALL NOT block user deletion; preserve the historical record according to the domain/persistence constraints.

#### Scenario: Current or future ticket blocks user deletion
- **GIVEN** `SYSTEM DATE;2026-10-01` and a ticket dated `2026-10-15` for Ana
- **WHEN** `USER DELETE;ana@correo.com;Clave1!` is executed
- **THEN** deletion is rejected and the user and ticket remain intact.

#### Scenario: Historical ticket no longer blocks deletion
- **GIVEN** the ticket in the preceding scenario and system date changed to `2026-10-16`
- **WHEN** user deletion is requested
- **THEN** that historical ticket does not, by itself, block deletion; its fiscal/historical information remains available.

#### Scenario: Future-only ticket refund
- **GIVEN** tickets dated before, equal to, and after the system date
- **WHEN** each is submitted to `TICKET DELETE`
- **THEN** only the future ticket may be removed.

### 4. Group tickets, discounts, and composition

**GTICKET-01** Creating a group ticket SHALL capture group membership at purchase time and create one constituent individual ticket per member. The group ticket SHALL own those constituent tickets by composition; those tickets SHALL reference their corresponding users.

**GTICKET-02** Group tickets and individual tickets SHALL support a common abstraction for operations applying to both types. The group ticket SHALL maintain the specified relationship to the originating group, represented in the UML.

**GTICKET-03** Group purchase pricing SHALL use the base individual-ticket price applicable at purchase and apply the following size brackets:

| Number of members | Discount |
|---|---:|
| Fewer than 3 | 0% |
| 3–5 | 10% |
| 6–10 | 20% |
| More than 10 | 50% |

**GTICKET-04** `GROUPTICKET CREATE;TG01;G01;2026-10-15` SHALL report `OK GROUP TICKET CREATED -> <Precio>` on success. The purchase SHALL not partially create its constituent tickets if it fails.

**GTICKET-05** A group with at least one associated group ticket dated today or later SHALL reject membership changes and group deletion. Its constituent users SHALL also respect the active-ticket deletion restriction. The restrictions SHALL be evaluated against the *current configured date*, not persisted as independent lock flags.

**GTICKET-06** `GROUPTICKET DELETE;<identifier>` SHALL delete a group ticket only if its date is strictly in the future, together with its constituent tickets, without partial deletion. The source examples use `TG01` for creation and `TG001` for deletion; treat both as examples of the identifier parameter, not as mandated identical values.

#### Scenario: Discount boundaries
- **GIVEN** a base price of €40
- **WHEN** groups of 2, 3, 6, and 11 users purchase tickets
- **THEN** totals are €80, €108, €192, and €220 respectively; separately test the 5/6 and 10/11 boundaries.

#### Scenario: Locked and unlocked group
- **GIVEN** a group ticket dated today or later
- **WHEN** group membership or deletion is requested
- **THEN** the request is rejected; once the associated group tickets are historical, that restriction no longer applies.

#### Scenario: All-or-nothing group-ticket deletion
- **GIVEN** a future group ticket with multiple constituent tickets
- **WHEN** the group ticket is deleted successfully
- **THEN** all constituents are deleted as part of the same operation; any unsuccessful attempt leaves the original state unchanged.

### 5. Attractions and visitor access

**ATTRACTION-01** Attractions SHALL store a unique identifier, name, maximum capacity, and references to the users currently present. Attractions SHALL be creatable with `ATTRACTION CREATE;A01;Tornado;20`.

**ATTRACTION-02** `ATTRACTION ENTER;<attractionId>;<ticketId>` SHALL accept a valid individual or group ticket for the *current* system date, respecting maximum capacity. For group tickets, entry SHALL be indivisible: all constituents enter or none enter.

**ATTRACTION-03** The system SHALL allow a present user to leave an attraction and free one occupied place, without revalidating the ticket date at exit. The source's example identifies the entrant using `ATTRACTION EXIT;A01;T001`; see the unresolved syntax question below before freezing the command contract.

**ATTRACTION-04** `ATTRACTION STATUS;<attractionId>` SHALL display identifier, name, total capacity, occupancy, available places, and currently present users. It SHALL report the actual current state independently of whether users entered individually or with a group ticket.

**ATTRACTION-05** Occupancy SHALL be runtime-only and empty on application startup, while attraction definitions SHALL persist. Shared handling of ticket types SHALL use suitable object-oriented mechanisms without duplicating business rules.

#### Scenario: Atomic capacity rejection
- **GIVEN** an attraction with three remaining places and a valid group ticket for four people
- **WHEN** the group enters
- **THEN** nobody enters and occupancy remains unchanged.

#### Scenario: Entry, exit, and status
- **GIVEN** an attraction with available capacity and a valid ticket
- **WHEN** a user enters, status is queried, and the user leaves
- **THEN** the reported occupancy increases and subsequently decreases, with available capacity updating accordingly.

#### Scenario: Date changes after admission
- **GIVEN** a user has entered with a ticket valid on the entry date
- **WHEN** the system date changes
- **THEN** the user may still leave, without date revalidation.

### 6. UML model

**UML-01** Create or update `uml/model.puml` as valid PlantUML, deriving the actual diagram from the current code **after** implementing the relevant F2 behaviors.

**UML-02** Show relevant classes, interfaces, enums, actual inheritance/implementation, navigable associations and compositions, directions, and inferable multiplicities. Relationships SHALL reflect actual references in code; do not invent reverse navigation.

**UML-03** Follow the additional source presentation restrictions: omit methods and usage relationships except the explicit no-incoming-relation exception; omit attributes that are represented as object relationships; remove technical attribute labels; use relationship names matching the containing fields; and apply the required cross marking for owning direction. If these presentation rules conflict, flag the conflict rather than silently redefining them.

**UML-04** UML generation SHALL NOT modify functional code merely to make the diagram match a preferred design.

#### Scenario: Diagram matches implementation
- **GIVEN** the final F2 implementation
- **WHEN** `uml/model.puml` is rendered
- **THEN** it is syntactically valid, depicts the actual implemented relationships and directionality, and contains no unimplemented elements.

### 7. Temporary persistence (`--fly`)

**FLY-01** With `--fly`, the application SHALL create an isolated per-run timestamp-identified temporary directory, e.g. `tmp/20260826_190315/`, and route **all** persistence repositories into it.

**FLY-02** Repository data-access logic SHALL be shared between normal and temporary mode; only configured storage paths SHALL differ.

**FLY-03** On controlled termination, including `EXIT`, the application SHALL delete the per-run temporary directory and its contents. Temporary execution SHALL NOT modify persistent data from a normal run.

**FLY-04** Temporary mode SHALL work both interactively and with a command file, e.g. `java -jar target/parque.jar --fly` and `java -jar target/parque.jar --fly input_fase2.txt`.

#### Scenario: Isolated run and cleanup
- **GIVEN** normal persistent data already exists
- **WHEN** a `--fly` session adds or modifies state and exits
- **THEN** its temporary files are removed, and a subsequent normal run observes the original permanent state.

#### Scenario: Shared functionality
- **GIVEN** equivalent commands run once normally and once with `--fly`
- **WHEN** the commands execute
- **THEN** business behavior is the same, while the chosen repository paths differ.

## Open design questions: do not silently decide

1. **Attraction exit identifier:** F2 source uses `ATTRACTION EXIT;A01;T001`, whereas the earlier full Delivery 2 text defined `ATTRACTION EXIT;<AttractionIdentifier>;<Email>`. Preserve the example and ask which is authoritative, or explicitly record the interpretation before implementation.
2. **UML representation:** the source requests both listing relevant public methods and, later, "Do not represent usage relationships or methods in classes." The more restrictive display rule appears later, but the documents conflict. Record a design decision before finalizing the diagram.
3. **Ticket ID generation:** the combined F2 text does not fully define identifiers for individual tickets composed by group tickets. Consult the authoritative Delivery 2 specification or clarify; do not improvise a scheme that may conflict with previously defined identifiers.
4. **Historical references:** the original combined prompt requires historical tickets to survive when users may be deleted, but leaves the reconstruction strategy unspecified. Specify a design that retains the necessary historical data without weakening user deletion rules.
5. **Attraction lifecycle:** the input says attractions restart empty. Persist definitions but not current occupants; verify no ambiguity with the persistence layer.

These are **questions and implementation considerations**, not additions to the requirements.

## Required OpenSpec artifacts and workflow

Use a single change identifier such as `f2-amusement-park-management` (adapt to the project's existing naming conventions). Before generating artifacts, inspect existing F1 specs, code, commands, and persistence behavior.

1. **`proposal.md`** — state *Why*, *What Changes*, in/out scope, dependencies, affected capabilities, impact and unresolved questions. Keep it concise rather than pasting the complete specification into every artifact.
2. **`design.md`** — describe the domain model, shared tickets abstraction, referential integrity and ownership, pricing and historical state, atomic group actions, current-date access, persistence path configuration, and startup/cleanup behavior. Document alternatives and decisions only where necessary.
3. **`specs/<capability>/spec.md`** — write normative ADDED/MODIFIED delta requirements with `#### Scenario:` cases. Each expected behavior in the source SHALL be represented; trace requirements and examples from this prompt to their spec entries.
4. **`tasks.md`** — produce a checkable sequence: review F1 baseline; date and pricing; groups; individual tickets; group tickets; attractions; persistence integration; `--fly`; tests; UML reflection; validation and regression.
5. **Verification** — validate the OpenSpec change, run Maven build/tests, execute positive/negative command scenarios, verify clean startup and restart, check discount boundaries and atomicity, verify `--fly` does not alter permanent files, and render the UML. Do not archive before verification succeeds.

The task order above is **implementation guidance**, not a request to split this source into separate proposals. When a decision is ambiguous, record and surface it during proposal/design review instead of inventing an unstated requirement. Keep the resulting implementation consistent with existing F1 command semantics.

## Definition of done

- All seven functional areas are covered in specs and implemented in the same coherent F2 change.
- Previously supported F1 commands and execution modes continue working.
- Normal persistence survives restart; `--fly` remains isolated and cleans up.
- Business invariants, failed operations, boundary prices, and capacity rules are tested.
- UML represents actual code and renders.
- OpenSpec artifacts validate, Maven build/tests pass, and remaining interpretation decisions are documented.
