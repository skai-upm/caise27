## Mandatory milestone (verbatim source)

### 17.8. F2-C08 — Complete park persistence

The application must be able to terminate and later reconstruct the required park state, including the new elements and their relationships. This milestone must also add temporary --fly persistence mode, using the same repositories configured to use an independent temporary directory that must be deleted at the end of execution.


## Detailed source requirements (verbatim excerpts)

## 13. Persistence

The addition of groups, tickets, and attractions extends the state that the application must preserve between runs. The solution must maintain the separation of responsibilities introduced in the first delivery. Data must be stored in text files and correctly reconstructed when the application starts again. Students must decide how to organize persistence of new elements and their relationships. The data needed to reconstruct the following must be preserved:

- groups and their users;
- individual tickets and their user;
- group tickets, their constituent individual tickets, and, while the group exists, the reference to the group that made the purchase;
- attractions.

The collection of users currently inside each attraction will not be persisted. At the start of a new execution, all attractions must be empty, regardless of their state when the previous execution ended. This extension may not be implemented through automatic Java object serialization. Databases, persistence frameworks, and external libraries are not permitted.

### 13.1. Temporary persistence mode

The application must support an optional temporary execution mode intended to facilitate testing without modifying the persistent data from a normal execution. When the JAR is run with the argument:

```text
--fly
```

at startup, the application must create an independent temporary directory identified by a timestamp. For example:

```text
tmp/20260826_190315/
```

During that execution, all repositories must use only files located inside that temporary directory. Temporary mode must cover all persistent system elements, including users, groups, tickets, and attractions. Repositories must not have an alternative implementation specific to this mode. The difference between normal and temporary persistence must be handled through configuration of repository paths. When execution ends, the created temporary directory and all its files must be deleted. This cleanup must occur both when the application ends through EXIT and when processing of a command file finishes normally. The --fly mode must be usable both interactively and with a command file. This feature extends the execution modes established in Phase 1. Without --fly, argument behavior must remain exactly as in the previous delivery. With --fly, it appears as the first argument and may optionally be followed by a command file path. Accordingly, the following forms of execution must be supported:

```text
java -jar target/nombre-aplicacion.jar
java -jar target/nombre-aplicacion.jar input_fase2.txt
java -jar target/nombre-aplicacion.jar --fly
java -jar target/nombre-aplicacion.jar --fly input_fase2.txt
```

When --fly is not used, the application must retain its normal permanent-persistence behavior. The purpose of this mode is to enable isolated, repeatable executions without altering the persistent state used by other executions.
