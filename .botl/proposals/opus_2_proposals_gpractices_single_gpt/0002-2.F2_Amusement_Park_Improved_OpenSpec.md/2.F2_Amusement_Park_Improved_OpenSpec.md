## 3. Central park management

The application must have a single object responsible for managing the overall state of the park during execution. This object will centralize access to the users, groups, tickets, and attractions existing in the system, and allow operations that relate these elements to be performed. No more than one instance of this object may exist during the same execution of the application. The chosen design must guarantee this regardless of where in the application access to central management is requested.

### 4.1. Current system date

Park operations will depend on a current date. When the application starts, the system date will be the local date at the time execution begins. To facilitate testing, this date may be replaced during execution and must not depend solely on the actual date of the computer running the application. The following command will be added:

```text
SYSTEM DATE;<yyyy-MM-dd>
```

For example:

```text
SYSTEM DATE;2027-04-15
```

From that moment on, all date-dependent operations must regard April 15, 2027, as the current system date. The date may be modified as many times as necessary during a single execution.

### 4.2. Current ticket price

The system will maintain a current base ticket price. At the start of each execution, this price will be 40.00 euros. The price may be modified during execution using:

SYSTEM PRICE;<Price>

For example:

```text
SYSTEM PRICE;45.50
```

The specified price must represent a valid, positive monetary amount. The current system price will be used as the base price for new tickets created from that moment onward. Changing the price will not alter the price of tickets already created. For group tickets, the corresponding discount will be applied to the current system base price at the time of purchase. The value set with SYSTEM PRICE will affect only the current execution. When a new execution begins, the price will revert to 40.00 euros.

## 5. User groups

Registered users may be organized into groups. Each group will have a unique identifier, a name, and will consist of users who already exist in the system. A group is created using:

GROUP CREATE;Identifier;Name

For example:

```text
GROUP CREATE;G01;Familia Garcia
```

To add an existing user to a group, use:

GROUP ADD;Identifier;Email

For example:

```text
GROUP ADD;G01;ana@correo.com
GROUP ADD;G01;pedro@correo.com
```

The same user may not appear more than once in the same group. GROUP ADD must reject the addition of a user who already belongs to that group. A group may be created empty and users added progressively. It must also be possible to remove a user from a group while the group is modifiable:

GROUP REMOVE;Identifier;Email

A group may also be deleted using:

GROUP DELETE;Identifier

Deletion is permitted only if there is no group ticket associated with that group whose date is equal to or later than the current system date. Group tickets for earlier dates alone will not prevent deletion of the group. If the group has a future ticket, it may first be deleted using GROUPTICKET DELETE. A ticket for the current day cannot be deleted and will continue to prevent deletion of the group. A group has an active group ticket when at least one associated group ticket has a date equal to or later than the current system date. GROUP ADD and GROUP REMOVE may be performed only when the group has no associated active group tickets. Group tickets for earlier dates are considered historical and will not prevent group modification. If a future ticket is deleted using GROUPTICKET DELETE, the application must check again whether other active group tickets remain associated with the group. If none remain, the group can be modified again. The group’s locked state must not be stored as an independent attribute; instead, it must be determined from the existing tickets and the current system date.

## 7. Tickets

To access attractions, users must have a ticket valid for the corresponding date. Individual tickets and group tickets are different types of ticket but share information and behavior. All tickets must have, at a minimum:

- a unique identifier;
- a date of use;
- information about their price.

All ticket types will share a common identifier space. An individual ticket and a group ticket may not simultaneously have the same identifier. This restriction must be checked in a common manner for the different ticket types. When creating a group ticket, it must also be checked that none of the identifiers derived for its constituent individual tickets conflicts with an existing ticket. If any identifier conflict occurs, the group ticket must not be partially created.

### 7.1. Relationship between ticket types

The design must use object-oriented inheritance mechanisms, through class extension and/or interface implementation, to represent the common behavior of the different ticket types. Individual and group tickets may not be implemented as two entirely independent classes that duplicate common logic. In particular, price-related behavior and elements common to all ticket types must be reused. The design must allow different types of ticket to be handled through a common abstraction when an operation does not need to know the concrete type. Choosing a base class, an abstract class, an interface, or a combination of these mechanisms is part of the design to be carried out by the student.

### 7.2. Individual ticket

An individual ticket will be associated with a single user. The creation command will be:

TICKET CREATE;<identifier>;<email>;<date>

For example:

```text
TICKET CREATE;T001;ana@correo.com;2027-04-15
```

The identifier must be unique among all tickets in the system. The user must already exist in the system. The specified date must be equal to or later than the current system date. Tickets may not be created for past dates. The ticket will be valid only on the date specified at creation. The price of a new ticket will be the current base price configured in the system. If SYSTEM PRICE has not been used during the execution, the initial price of 40.00 euros will apply. When a ticket is successfully created, the application must display the price that will be charged for it. An individual ticket must hold a reference to the user for whom it was purchased. This relationship is unidirectional: the ticket knows the user, but the user must not maintain references to their tickets. An individual ticket may be deleted using:

TICKET DELETE;<identifier>
