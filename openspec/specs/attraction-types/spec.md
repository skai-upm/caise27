# attraction-types Specification

## Purpose

Specialises attractions by the kind of ticket they admit, using access-capability interfaces and bounded generic types so that incompatible ticket kinds are excluded by design.

## Requirements

### Requirement: Attraction types and admitted tickets
The system SHALL support the attraction types `GENERAL`, `INDIVIDUAL`, `GROUP` and `SPECIAL`. `GENERAL` SHALL admit individual tickets and group tickets; `INDIVIDUAL` SHALL admit only individual tickets; `GROUP` SHALL admit only group tickets; `SPECIAL` SHALL admit only individual tickets, as the basis for its additional Special Pass rules. Tickets generated by a group ticket are individual tickets. An entry with a ticket kind the attraction does not admit SHALL be rejected with `ERROR` and admit nobody; all other entry rules (date, capacity, atomicity) are unchanged.

#### Scenario: GROUP rejects an individual ticket
- **GIVEN** `A02` is a `GROUP` attraction and `T001` is an individual ticket for today
- **WHEN** `ATTRACTION ENTER;A02;T001` is processed
- **THEN** the result starts with `ERROR` and nobody enters

#### Scenario: INDIVIDUAL rejects a group ticket
- **GIVEN** `A03` is an `INDIVIDUAL` attraction and `TG01` is a group ticket for today
- **WHEN** `ATTRACTION ENTER;A03;TG01` is processed
- **THEN** the result starts with `ERROR`, while `ATTRACTION ENTER;A03;T001` succeeds

#### Scenario: GENERAL admits both
- **WHEN** `T001` and `TG01` are used to enter a `GENERAL` attraction with enough places
- **THEN** both entries succeed

#### Scenario: SPECIAL uses individual tickets
- **GIVEN** `A04` is a `SPECIAL` attraction
- **WHEN** `ATTRACTION ENTER;A04;T001` and `ATTRACTION ENTER;A04;TG01` are processed
- **THEN** the individual ticket is admitted and the group ticket is rejected with `ERROR`

### Requirement: Access capabilities as interfaces and bounded generics
Ticket access capabilities SHALL be represented by interfaces (a common access capability, an individual-access capability and a group-access capability implemented by the corresponding ticket classes), and each attraction type SHALL be a class whose generic type parameter is bounded by the capability it admits, so that entering an attraction with an incompatible capability does not compile. Entries resolved from command identifiers at run time SHALL be checked against the same bound before use.

#### Scenario: Design inspection
- **WHEN** the attraction classes are inspected
- **THEN** a `GROUP` attraction's entry operation only accepts the group-access capability type, an `INDIVIDUAL` or `SPECIAL` attraction's only the individual-access capability type, and a `GENERAL` attraction's the common capability

### Requirement: Status shows the type
`ATTRACTION STATUS` SHALL also show the attraction's type on its first line.

#### Scenario: Status of a typed attraction
- **WHEN** `ATTRACTION STATUS;A02` is processed for the `GROUP` attraction `A02` named `Coches` with capacity 10
- **THEN** the first line starts with `OK: Attraction A02 (Coches) capacity=10 present=0 available=10` and contains `type=GROUP`
