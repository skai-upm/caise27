# park-persistence Specification

## Purpose

Defines how groups, tickets and attractions are kept between runs in text files, and the temporary `--fly` mode that isolates a run from the permanent data.

## Requirements

### Requirement: Park state survives restarts
Groups with their members, individual tickets with their user, group tickets with their individual tickets and (while it exists) their group, attractions with their type, and SpeedPasses and Special Passes with their individual ticket, stored price and consumed state SHALL be stored in text files, without Java serialization or databases, and reconstructed when the application starts. Every successful state-changing command SHALL be persisted before the next command.

#### Scenario: Reload park
- **WHEN** a group, an individual ticket, a group ticket and an attraction are created, the application exits and starts again
- **THEN** the same group members, tickets (identifiers, dates, prices, composition) and attractions are available

#### Scenario: Reload passes and types
- **WHEN** a SPECIAL attraction exists, T001 has a consumed SpeedPass, an unconsumed SpeedPass and a Special Pass, and the application restarts
- **THEN** the attraction is still SPECIAL and T001's passes keep their identifiers, prices and consumed states

### Requirement: Occupancy is not persisted
The users inside attractions SHALL NOT be persisted; every attraction SHALL be empty when a new execution starts.

#### Scenario: Attractions start empty
- **WHEN** users are inside A01 when the application exits and it is started again
- **THEN** `ATTRACTION LIST;A01` reports no users

### Requirement: Historical tickets of deleted users and groups are persisted
Persistence SHALL keep enough information to reconstruct historical tickets whose user or group has been deleted, including the holder's DNI, email and name.

#### Scenario: Deleted user's ticket after restart
- **WHEN** a user with only historical tickets is deleted and the application restarts
- **THEN** the historical tickets are still present with the holder's DNI and email

### Requirement: Temporary persistence mode
When `--fly` is the first argument (optionally followed by a command file), the application SHALL create a new directory `tmp/<yyyyMMdd_HHmmss>/`, make every repository read and write only there, and delete that directory and its files when execution ends via `EXIT`, end of input or end of the command file. The same repositories SHALL be used as in normal mode, configured with different paths. Permanent data SHALL NOT be read or modified.

#### Scenario: Isolated interactive run
- **WHEN** the JAR is started with `--fly`, a user is created, and `EXIT` is processed
- **THEN** the permanent `users.txt` is unchanged and the temporary directory no longer exists

#### Scenario: Fly mode with a command file
- **WHEN** the JAR is started with `--fly input_fase2.txt`
- **THEN** the file's commands run against an initially empty park and no data generated by the run remains afterwards

### Requirement: Untyped attraction records
Attraction records without a type, as written by Delivery 2, SHALL be loaded as `GENERAL` attractions.

#### Scenario: Delivery 2 data
- **WHEN** the attraction file contains `A01;Dragon Rojo;20`
- **THEN** A01 is loaded as a GENERAL attraction with capacity 20
