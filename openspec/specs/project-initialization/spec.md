# project-initialization Specification

## Purpose

Defines the build baseline of the Amusement Park application: a Maven project with the quickstart archetype structure that targets JDK 21 and compiles with Maven.

## Requirements

### Requirement: Maven project structure
The repository SHALL contain a Maven project at its root with a `pom.xml` and the standard `maven-archetype-quickstart` directory layout (`src/main/java` for production sources and `src/test/java` for test sources).

#### Scenario: Standard structure present in a clean checkout
- **GIVEN** a clean checkout of the repository
- **WHEN** the project root is inspected
- **THEN** a `pom.xml` file exists at the root
- **AND** the directories `src/main/java` and `src/test/java` exist and contain Java sources

#### Scenario: Non-standard structure is not acceptable
- **GIVEN** a checkout in which `pom.xml` is missing from the root
- **WHEN** a Maven build is attempted
- **THEN** the build fails because no Maven project is found, which violates this requirement

### Requirement: JDK 21 target
The Maven project SHALL be configured to compile sources for Java 21.

#### Scenario: Compiler release configured to 21
- **WHEN** the `pom.xml` is inspected
- **THEN** the Java compiler release (or source/target) is configured as `21`

#### Scenario: Compiled bytecode targets Java 21
- **GIVEN** the project has been compiled
- **WHEN** the class file version of a compiled production class is inspected
- **THEN** it corresponds to Java 21 (class file major version 65)

### Requirement: Maven compilation succeeds
The project SHALL compile and run its tests successfully with Maven using a JDK that supports Java 21.

#### Scenario: Build from a clean checkout
- **GIVEN** a clean checkout, JDK 21 (or newer) and Maven available
- **WHEN** `mvn clean test` is executed at the repository root
- **THEN** compilation succeeds and the build finishes with `BUILD SUCCESS`

#### Scenario: Compilation error breaks the build
- **GIVEN** a source file containing a compilation error
- **WHEN** `mvn compile` is executed
- **THEN** the build fails, so the baseline is only satisfied when all sources compile

### Requirement: Delivery 1 technical restrictions
The application SHALL use only the Java standard library at runtime (no databases, frameworks or external libraries; test-only dependencies excluded), SHALL persist data only in text files, SHALL NOT use regular expressions or encryption mechanisms in its production code, and SHALL interpret commands with basic String operations and `split`.

#### Scenario: No runtime dependencies
- **WHEN** the Maven dependencies are listed
- **THEN** every declared dependency has `test` scope

#### Scenario: No regular expressions or encryption in production code
- **WHEN** the production sources are inspected
- **THEN** they use no `java.util.regex`, no `matches`/`replaceAll`/`replaceFirst`, no `split` with a regular-expression pattern, and no `javax.crypto` or `java.security.MessageDigest`

#### Scenario: Basic execution example works from a clean build
- **GIVEN** `mvn package` has been run on a clean checkout
- **WHEN** the assignment's basic example (create Ana and Pedro, update Ana's phone and email, delete Pedro, HELP, EXIT) is run interactively and as a command file
- **THEN** both runs print `USER CREATED`, `USER CREATED`, `USER UPDATED`, `USER UPDATED`, `USER DELETED`, the help text and the exit acknowledgement, and leave only Ana (with the new phone and email) in `users.txt`

### Requirement: Delivery 2 technical restrictions
Delivery 2 SHALL keep all Delivery 1 restrictions and additionally: persistence MUST NOT use Java object serialization; a single central park manager instance SHALL exist; in-memory domain relationships SHALL be object references and collections with the required directions (attraction → users inside, individual ticket → user, group ticket → composition and → group while it exists, no references from users or groups to tickets); ticket types SHALL share a common abstraction; and `--fly` SHALL reuse the same repositories changing only the data path.

#### Scenario: No serialization in production code
- **WHEN** the production sources are inspected
- **THEN** they do not use `Serializable`, `ObjectOutputStream` or `ObjectInputStream`

#### Scenario: Relationship directions in the model
- **WHEN** the fields of `User` and `Group` are inspected
- **THEN** neither has a field referencing tickets or attractions

### Requirement: Delivery 2 end-to-end execution
After `mvn package`, the JAR SHALL run a command file combining Delivery 1 and Delivery 2 commands both normally and with `--fly`, producing the same responses from the same initial state; after the `--fly` execution no data generated by it SHALL remain.

#### Scenario: Same command file, normal and fly
- **GIVEN** an empty working directory and a command file that creates users, a group, individual and group tickets, an attraction, enters and leaves it and shows its status
- **WHEN** it is run with `--fly <file>` and then with `<file>`
- **THEN** both runs print the same responses without `ERROR` lines, the temporary directory no longer exists after the first run, and only the normal run leaves data files
