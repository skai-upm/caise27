# Design

## Context

Delivery 2 code: packages `model`, `validation`, `repository`, `controller`, `cli` under `es.upm.etsisi.amusementpark`; `ParkController` is a singleton that builds the repositories itself in `initialize(dataDir)`; other controllers are plain objects created inside `CommandProcessor`; failures are `IllegalArgumentException`; `App` handles `--fly`. See proposal.md for scope; specs for behaviour.

## Goals / Non-Goals

**Goals:** layered packages; exception hierarchy; Builder for invoices; Singleton controllers with injected repositories/collaborators; strategy-injected help; BCrypt; passes; generic attraction types; persistence + UML updates; all D1/D2 behaviour kept.

**Non-Goals:** repository interfaces with alternative back-ends (only file-based repositories exist; they are made replaceable by being created and injected at initialization); migrating old plain-text user files.

## Decisions

1. **Packages.** `presentation` (`CommandProcessor`, `CommandRunner`, `help.*`), `business.model`, `business.controller`, `business.validation`, `business.invoice`, `business.security`, `business.exception`, `persistence` (repositories, file stores, `LineFile`, `DataDirectory`, `PersistenceException`). `App` and `ApplicationInitializer` stay in the root package as the composition root (keeps `Main-Class`).
2. **Exceptions.** `business.exception.ParkException` (abstract, unchecked) with `ValidationException` (bad data/format), `NotFoundException`, `DuplicateException`, `AuthenticationException`, `OperationNotAllowedException` (locks, dates, capacity, type, pass state). `persistence.PersistenceException` wraps I/O errors. `CommandProcessor` catches `ParkException` → `ERROR: <msg>`, `PersistenceException` → `ERROR: persistence failure: <msg>`, any other `RuntimeException` → generic error; processing always continues.
3. **Singletons + DI.** Each controller (`ParkController`, `UserController`, `GroupController`, `TicketController`, `PassController`, `AttractionController`, `InvoiceController`) has a private constructor, `getInstance()`, and a `configure(...)` method receiving its dependencies. `ApplicationInitializer.initialize(dataDir[, hasher])` builds a `persistence.Repositories` record via `Repositories.fileBased(dataDir)`, injects it into `ParkController`, injects `ParkController` and collaborators into the others (`UserController` ← `PasswordHasher`; `AttractionController` ← `PassController`; `TicketController` ← `PassController` for cascades), builds `HelpGenerator` with its formatters, and returns a `CommandProcessor` that receives the controllers. `--fly` only changes `dataDir`. Alternative (repositories as singletons) is forbidden by the source.
4. **Help.** `presentation.help.HelpFormatter` (strategy: `String format(List<CommandDescriptor>)`), implementations `SyntaxHelpFormatter` and `ExtendedHelpFormatter`; `HelpGenerator` receives a `Map<HelpMode, HelpFormatter>` by constructor and is injected into `CommandProcessor`. Command registrations carry syntax + description, so help lists exactly what is parsed. Variants with different field counts (`ATTRACTION CREATE` 4/5, `ATTRACTION ENTER` 3/4) are separate registrations under one name, chosen by field count.
5. **Passwords.** `business.security.PasswordHasher` interface; `BCryptPasswordHasher(logRounds)` (default 10; tests inject 4 for speed). `User` stores `passwordHash`; `UserController` validates the raw password, hashes, and verifies with `hasher.matches`. jbcrypt bundled with maven-shade-plugin (`finalName nombre-aplicacion`), so `java -jar` needs no classpath.
6. **Passes.** `abstract Pass` (id, `IndividualTicket ticket`, stored `price`, `consumed`) → `SpeedPass`, `SpecialPass`. Pass → ticket is unidirectional; `PassRepository` answers by ticket. Shared pass id space (speed + special). Price = `ticket.getPrice()` × 20% (HALF_UP, 2 decimals) or × 100%. Special Pass uniqueness: at most one existing Special Pass per ticket (a refunded one no longer exists, so a new one may be bought — flagged ambiguity: "throughout its entire existence" vs. refunds that remove the pass from persisted state).
7. **Attractions with generics.** Access capability interfaces in `business.model`: `TicketAccess` (holders, individual tickets, validity), `IndividualAccess extends TicketAccess` (implemented by `IndividualTicket`), `GroupAccess extends TicketAccess` (implemented by `GroupTicket`). `abstract Attraction<T extends TicketAccess>` holds `Class<T> accessType` and offers `enter(T ticket, boolean speed, PassLookup passes)`: it collects passes to consume (`passesToConsume`, overridden by `SpecialAttraction`), checks capacity/duplicates, then adds occupants and consumes passes — all-or-nothing. Subclasses: `GeneralAttraction extends Attraction<TicketAccess>`, `IndividualAttraction extends Attraction<IndividualAccess>`, `GroupAttraction extends Attraction<GroupAccess>`, `SpecialAttraction extends Attraction<IndividualAccess>` (no SPEED, requires unconsumed Special Pass). `AttractionType` enum creates them. The controller narrows a `Ticket` to `T` through `accessType.cast` after `accepts(ticket)`; the generic parameter thus constrains `enter`. `PassLookup` is a business interface implemented by `PassController`.
8. **Invoices (Builder).** Product `Invoice` (header lines, `List<InvoiceSection>`, total) with `toText()`. `InvoiceSection(title, items, charged)`; only charged sections add to the total; empty sections are never added. Abstract `InvoiceBuilder` (common steps: `reset`, `addHeaderLine`, `addSection`, `build`), concrete `UserInvoiceBuilder` (`forUser`, `withTickets`, `withSpeedPasses`, `withSpecialPasses`) and `GroupInvoiceBuilder` (`forGroup`, `withGroupTickets` adding one charged section of group tickets plus informational composition sections). `InvoiceController` acts as director, gathering data from repositories.
9. **Persistence.** `attractions.txt`: `id;name;capacity;type` (3 fields → GENERAL). `passes.txt`: `SPEED|SPECIAL;id;ticketId;price;consumed`, loaded after tickets and linked to the individual ticket object by id. Repositories self-save on add/remove and expose `save()`.
10. **Outputs.** `SPEEDPASS CREATED - <n> pass(es) - TOTAL PRICE: <x> EUR`, `SPECIALPASS CREATED - PRICE: <x> EUR`, `SPEEDPASS DELETED`, `SPECIALPASS DELETED`, entry adds `SPEEDPASS CONSUMED: <ids>` or `SPECIALPASS CONSUMED: <id>`; invoices print a titled multi-line block ending with `TOTAL: <x> EUR`.

## Risks / Trade-offs

- [Large package move] → done mechanically first with all tests green before adding features.
- [Singletons hold state across tests] → `ApplicationInitializer.initialize` reconfigures every singleton; tests always initialise in `@BeforeEach`.
- [BCrypt slows tests] → injected hasher with low cost in tests; production cost 10.
- [Old users files with plain passwords will not authenticate] → migration explicitly not required.
- [Mandatory per-milestone commits] → one BOTL commit, messages listed in body.
