# Design

## Context

The repository contains only OpenSpec scaffolding; there is no Java code. The machine has Maven 3.9 running on JDK 24 and no JDK 21 installation, so "compile with JDK 21" is met by compiling with `maven.compiler.release=21` (the compiler enforces the Java 21 API and bytecode level). The archetype `maven-archetype-quickstart` 1.5 is available in the local Maven repository; it generates JUnit 5 tests.

## Goals / Non-Goals

**Goals:**
- The smallest class structure that satisfies the mandated separation (User / main class / persistence class) while keeping command handling shared between interactive and file modes.
- Every rule in the specs covered by a JUnit test.

**Non-Goals:**
- Layered packages, interfaces, design patterns, dependency injection, encryption (later deliveries).
- Concurrency or multi-process access to the data file.

## Decisions

### Project coordinates and packaging
`groupId=es.upm.parque`, `artifactId=parque`, package `es.upm.parque`, generated by `mvn archetype:generate` with archetype version 1.5. `finalName` is `parque` so the JAR is `target/parque.jar` (the name later deliveries use). `maven-jar-plugin` sets `Main-Class: es.upm.parque.App`. Since there are no runtime dependencies, a plain JAR is executable; no shade/assembly plugin is needed.

### Classes (single package `es.upm.parque`)
- `User` — encapsulated state; `dni` is `final` with no setter. Knows nothing about files.
- `UserField` — enum `NAME, SURNAME, EMAIL, PASSWORD, PHONE, CARD` used by `USER UPDATE`.
- `UserValidator` — static checks for DNI, email, password, card, non-blank text. Pure functions, easy to test; keeps `User` a plain data holder.
- `UserRepository` — reads/writes the `;`-separated file; `List<User> load()` and `void saveAll(Collection<User>)`. Path given in the constructor (default `data/users.txt`); parent directory created on save.
- `UserManager` — in-memory list of users loaded from the repository; `create`, `delete`, `update` with uniqueness and authentication; persists after each successful change. Errors are signalled with an unchecked `UserException` carrying a user-facing message.
- `CommandProcessor` — splits a line with `split(";", -1)`, dispatches on the first component, returns a result (`output` text + `exit` flag). This is the single implementation used by both modes.
- `App` — `main`: chooses the input source (stdin or file from `args[0]`), wraps it in a `BufferedReader`, and runs the shared loop: skip blank lines, pass each line to `CommandProcessor`, print output, stop on exit or end of input.

Alternative considered: putting command dispatch in `App`. Rejected because the specs require one shared processing path and the main class should only handle terminal interaction; a separate processor is also directly unit-testable.

### Parsing
`split(";", -1)` keeps trailing empty fields so `USER CREATE;...;` with an empty card is detected as an invalid value rather than a short command. The command name is the first component trimmed; it is compared case-sensitively against `USER CREATE`, `USER DELETE`, `USER UPDATE`, `HELP`, `EXIT`. Parameter count must match exactly.

### Output conventions
Success: `OK USER CREATED`, `OK USER DELETED`, `OK USER UPDATED`. Failure: `ERROR: <reason>`. `EXIT` prints `OK EXIT`. In file mode each command is echoed as `> <command>` before its output so the run log is readable; interactive mode does not echo.

### Validation details
- DNI: length 9, first 8 `Character.isDigit`, letter = `"TRWAGMYFPDXBNJZSQVHLCKE".charAt(n % 23)`; lowercase letter accepted and normalised to uppercase.
- Email: exactly one `@` (`split("@", -1).length == 2`), local part non-empty, domain contains `.`, text before the last `.` non-empty, text after the last `.` length 3, no whitespace.
- Password: loop over chars with `Character.isUpperCase/isLowerCase/isDigit`; symbol = not letter/digit/whitespace.
- Email uniqueness compared with `equalsIgnoreCase`; login lookup by email is also case-insensitive.

### Persistence
Whole-file rewrite after each change (data set is small; simplest correct approach). UTF-8 encoding. Lines with a field count other than 7 or invalid DNI are skipped with a warning on stderr. Field values cannot contain `;` because commands are split on it.

## Risks / Trade-offs

- [No real JDK 21 locally] → `release=21` guarantees Java 21 API/bytecode compatibility; the build is portable to a JDK 21 machine.
- [Passwords stored in plaintext] → Required by this delivery (no encryption); a later delivery introduces hashing.
- [Relative data path depends on working directory] → Documented; tests use temporary directories via constructor injection of the path.
