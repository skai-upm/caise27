# Design

## Context

Greenfield: the repository holds only OpenSpec scaffolding, a README and a Maven-oriented `.gitignore`. See proposal.md for motivation. Delivery-1 restrictions shape every decision: Java 21, Maven standard structure, Java standard library only at runtime, no regular expressions, no databases/frameworks/encryption, command parsing with basic `String` operations and `split`, and separate classes for the user, the application entry point and persistence.

The build machine has a newer JDK installed; the project targets Java 21 through `maven.compiler.release=21`, which produces Java 21 bytecode and restricts the API to Java 21.

## Goals / Non-Goals

**Goals:**
- One shared command pipeline used identically by interactive and file mode.
- Rejected commands never mutate in-memory or persisted state.
- Each layer (parsing, business rules, persistence) independently testable.

**Non-Goals:**
- Features from later deliveries (groups, tickets, attractions, etc.).
- Password hashing or telephone validation (explicitly not required in delivery 1).
- Localised or fixed output wording beyond what the source illustrates.

## Decisions

1. **Coordinates and layout.** `groupId` `es.upm.etsisi`, `artifactId` `amusement-park`, base package `es.upm.etsisi.amusementpark`, standard `src/main/java` and `src/test/java` layout as generated by `maven-archetype-quickstart`.
2. **JAR name.** The source repeatedly uses the literal path `target/nombre-aplicacion.jar`. The build sets `<finalName>nombre-aplicacion</finalName>` so every documented command works verbatim. Alternative (project-specific name) rejected because commands and paths are contractual.
3. **Executable JAR.** `maven-jar-plugin` writes `Main-Class` into the manifest. No shading is needed because there are no runtime dependencies.
4. **Classes (flat package).**
   - `App` — entry point; chooses standard input or the file named by `args[0]`, wires collaborators. Contains no file read/write logic for users.
   - `User` — encapsulated attributes; `dni` is `final` and has no setter.
   - `UserField` — enum `NAME, SURNAME, EMAIL, PASSWORD, PHONE, CARD`.
   - `UserValidator` — static checks for DNI, email, password and card using character inspection and `split` only.
   - `UserRepository` — loads/saves all users from/to the text file; the only class doing user file I/O.
   - `UserService` — create/delete/update rules, uniqueness, atomic persistence.
   - `CommandProcessor` — parses one line with `split(";", -1)`, dispatches, prints results; also runs a `BufferedReader` line by line so both input modes share it.
   - `UserException` — checked exception carrying a user-facing rejection reason.
   Alternative (layered packages, design patterns) rejected: the source states design patterns are not required in this delivery.
5. **Atomicity.** `UserService` validates everything first, then applies the change to a copy of the user list, saves the copy, and only then replaces the in-memory list. A failed save leaves memory unchanged and reports an error.
6. **Persistence format.** One user per line: `FirstName;Surnames;DNI;Email;Password;Phone;Card`, exactly the source example. Default file `users.txt` in the working directory; the path is a constructor parameter so tests use temporary files. A missing file means "no users yet". Lines that do not have seven fields or fail validation/uniqueness are skipped with a warning so start-up never crashes.
7. **Email rule.** `split("@", -1)` must give exactly two non-empty parts; the part after `@` must contain a `.` whose prefix (domain) is non-empty and whose suffix (extension) is exactly three characters, and no part may be empty. This accepts `ana@correo.com`, `ana.nueva@correo.com`, and rejects all listed invalid examples.
8. **Password rule.** At least one uppercase letter, one lowercase letter, one digit and one symbol, where a symbol is any character that is not a letter, digit or whitespace (`Character` methods, no regex).
9. **DNI rule.** Exactly nine characters: eight ASCII digits plus an uppercase letter equal to `"TRWAGMYFPDXBNJZSQVHLCKE".charAt(number % 23)`.
10. **Output.** Success lines `USER CREATED`, `USER DELETED`, `USER UPDATED` (as in the source example); rejections print `ERROR: <reason>` and processing continues. `EXIT` prints `BYE` and stops reading input.
11. **Tests.** JUnit 5 (`junit-jupiter`, test scope only), matching the current quickstart archetype. Test-only dependencies do not ship in the JAR, so the "standard library only" restriction applies to runtime code.

## Risks / Trade-offs

- [Source examples break `Clave1!` across two lines (`Clave1` / `!;612345678;...`), apparently a PDF wrapping artifact] → Treat each command as one physical line; the examples are read as `Clave1!`. A literally split line is rejected as malformed without crashing.
- [Skipping malformed stored lines drops them at the next save] → Warning is printed on load so the loss is visible; malformed data can only appear from manual edits.
- [Fields containing `;` cannot be represented] → Impossible by construction: commands are split on `;`, so no value can contain it.
- [Uppercase-only DNI letter] → Matches the source examples; lowercase letters are rejected.

## Migration Plan

Greenfield; no migration. Rollback is reverting the change's commit.

## Open Questions (flagged, not resolved by invention)

- **Mandatory milestone commits.** The source requires 11 separate Git commits with exact messages (`[F0-C01] …` to `[F1-C09] …`). This change is executed by a batch orchestrator that records one commit per proposal, so these commit messages cannot be reproduced individually within this lifecycle. The conflict is recorded here rather than silently resolved; the code itself covers every milestone.
- **Telephone/name content.** The source sets no validation for telephone, first name or surnames, so none is applied beyond field presence.
