# Design

## Context

The repository contains only OpenSpec scaffolding, a README and a LICENSE — no Java code. This change creates the Delivery 1 application from scratch (see proposal.md — Why). Constraints from the source: Java 21, Maven Quickstart layout, Java standard library only, no regular expressions, no databases/frameworks/external libraries/encryption, command parsing with String operations and `split`, separate user / main / persistence classes, encapsulated attributes.

The machine running the build has JDK 24/25 but no JDK 21 installed; Maven runs on JDK 24.

## Goals / Non-Goals

**Goals:**
- A small, layered command-line application whose command processing is shared by interactive and file modes.
- Validation logic reusable by both creation and update.
- Atomic commands: a rejected command never leaves partial in-memory or persisted state.
- Every spec scenario covered by a JUnit test or an executable command-file check.

**Non-Goals:**
- Features of later deliveries (tickets, attractions, groups, passes, encryption, design patterns).
- Output message localisation or exact wording beyond the examples (source §16 says messages may vary).
- Concurrency or multi-process access to the data file.

## Decisions

### D1. Project coordinates and build
- Generate with `maven-archetype-quickstart` (version 1.5, available in the local Maven cache), then set `maven.compiler.release` to `21`. `release=21` makes javac on JDK 24 enforce the Java 21 API and bytecode level, which satisfies "configured to use JDK 21" without a locally installed JDK 21. Alternative (requiring a JDK 21 toolchain) was rejected because none is installed.
- `groupId=es.upm.etsisi`, `artifactId=amusement-park`, base package `es.upm.etsisi.park`.
- `<finalName>amusement-park</finalName>` so the artifact is `target/amusement-park.jar`. The source's `target/nombre-aplicacion.jar` is read as a placeholder ("application-name"); **flagged ambiguity** — if the literal name is required, only `finalName` changes.
- `maven-jar-plugin` manifest `mainClass=es.upm.etsisi.park.App`. No shading — there are no runtime dependencies. JUnit Jupiter stays test-scoped (as generated by the archetype); it is not part of the runtime and is consistent with "standard library only" for the application.

### D2. Class structure (flat package for Delivery 1)
| Class | Responsibility |
|---|---|
| `App` | Entry point: chooses interactive vs file mode, wires components. No file I/O for user data. |
| `CommandProcessor` | Single parser/executor: `split(";", -1)`, dispatch on command keyword, returns a result (message + whether to stop). Used by both modes. |
| `CommandRunner` | Reads lines from a `BufferedReader` (stdin or file), skips blank lines, feeds `CommandProcessor`, stops on EXIT. Reading command *input* is not user-data persistence. |
| `User` | Encapsulated entity; `dni` is `final` with no setter. |
| `UserField` | Enum `NAME, SURNAME, EMAIL, PASSWORD, PHONE, CARD`. |
| `UserValidator` | Static validation of DNI, email, password, card — no regex. |
| `UserService` | Business operations create/delete/update: validation, uniqueness, credential checks, atomicity; delegates storage to the repository. |
| `UserRepository` | Text-file persistence: `load()` / `saveAll(Collection<User>)`, one user per line, `;`-separated. |
| `ValidationException` | Checked domain error carrying the user-facing reason. |

Alternative considered: putting operations in `CommandProcessor` directly. Rejected to keep parsing independent of business validation (proposal design consideration) and to make operations unit-testable without string parsing.

### D3. Atomicity and persistence strategy
- Each mutating operation validates everything first, then mutates the in-memory map, then rewrites the whole data file. If the write fails (`IOException`), the in-memory change is rolled back and an error is reported.
- Rewrite-whole-file is simplest for a small text file and keeps the file consistent with memory. The write goes to a temp file in the same directory and is moved over the target (`Files.move` with `REPLACE_EXISTING`, `ATOMIC_MOVE` when supported) so a crash mid-write does not corrupt existing data.
- Users are held in a `LinkedHashMap` keyed by email, preserving insertion order for the file. DNI uniqueness is checked by scanning (small data sets).

### D4. Data file location
The source does not name the file. Default: `users.txt` in the current working directory; overridable through the system property `park.users.file` (used by tests and for isolated runs). **Flagged ambiguity.**

### D5. Corrupt persisted lines
A stored line that does not split into exactly 7 fields is skipped with a warning on stderr at load time rather than aborting start-up. This keeps the application in a controlled state (F1-C09) without inventing a repair rule.

### D6. Parsing rules
- Each input line is `strip()`ped; blank lines are ignored (file mode explicitly; interactive mode the same, via the shared runner).
- `split(";", -1)` keeps trailing empty fields so the parameter count is exact. The first token is the command keyword: `USER CREATE`, `USER DELETE`, `USER UPDATE`, `HELP`, `EXIT`. Keywords are matched exactly (upper case, single space). **Flagged ambiguity** (case sensitivity unspecified).
- Expected parameter counts: CREATE 7, DELETE 2, UPDATE 4, HELP/EXIT 0. Wrong counts → `ERROR: ...`.
- Field values are not trimmed (names may contain spaces, e.g. `Garcia Lopez`).
- The source examples break `Clave1!` / `Otra2#` across two lines (`Clave1` newline `!`). This is treated as a document line-wrap artefact: the canonical command is a single line. **Flagged.**

### D7. Validation details
- DNI: length 9, chars 0–7 digits, char 8 equals `"TRWAGMYFPDXBNJZSQVHLCKE".charAt(number % 23)`. Only an upper-case letter is accepted. **Flagged** (case unspecified).
- Email: `split("@", -1)` must yield exactly 2 parts, local part non-empty; in the domain part the last `.` (via `lastIndexOf`) must have non-empty text before it and exactly 3 characters after it. Whitespace anywhere makes the email invalid.
- Password: at least one `Character.isUpperCase`, `isLowerCase`, `isDigit`, and one character that is not a letter, digit or whitespace (symbol). No minimum length is imposed (not in source).
- Card: length 16, all `Character.isDigit` restricted to ASCII `0`–`9`.
- Names, surnames and telephone: no validation (source only requires storage). A value containing `;` cannot arise because `;` is the separator.

### D8. Output
Success messages follow source §16: `USER CREATED`, `USER DELETED`, `USER UPDATED`. Errors are single lines prefixed `ERROR: `. `HELP` prints the five syntax lines from §11. `EXIT` prints `BYE` and stops. Unreadable/missing command file → `ERROR: cannot read file <path>` and exit status 1 (no stack trace).

### D9. Mandatory milestone commits
The source prescribes eleven separate commits (`[F0-C01] …` to `[F1-C09] …`). This change is executed by a batch harness that owns the Git history and records one commit per proposal; producing eleven commits inside the apply phase would also distort the SDDX per-phase git measurements. Therefore the milestone messages are **not** produced as separate commits in this run; tasks are still grouped and verified in checkpoint order. **Flagged conflict** between source and execution harness.

## Risks / Trade-offs

- [No JDK 21 locally] → `maven.compiler.release=21` enforces the Java 21 API; a JDK 21 machine builds the same sources unchanged.
- [Plain-text passwords in the data file] → Required by the source for Delivery 1 ("encryption mechanisms" are forbidden in this delivery).
- [Whole-file rewrite per command] → Fine for assignment-sized data; temp-file + move avoids corruption.
- [Placeholder JAR name] → Single `finalName` setting to change.
- [Exact-case command keywords] → Lower-case commands are rejected with an error, not crashed on.

## Migration Plan

Greenfield; no migration. Rollback is reverting the change's commit.
